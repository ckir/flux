# Cut 9f-1, plan 2: chunk checkpoints in the tree copy loop, and `--resume` of half-copied files

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A tree copy sends batched, digest-carrying chunk checkpoints of every large file (at least 64 MiB) to the merged WAL writer, and `--resume` continues each large partial from the last chunk it can PROVE (source and destination both match the recorded digest), never trusting an unproven byte.

**Architecture:** One `checkpoint` module in `flux-core` owns the run-level WAL handle (`Checkpoints`), a per-file sender (`FileSink`) and the resume decision (`decide`). `stage_file` gains one parameter, an optional per-file checkpoint context; it feeds a `ChunkHasher` from the bytes it writes, hands completed chunk digests to the WAL writer thread (which flushes at 1 s or 64 MiB), and at completion asks the writer for that file's failure. On resume `stage_file` validates the prior partial chunk by chunk before it opens it, truncates it to the proven offset and continues. The tree run opens the WAL once per operation after adoption, stops it before the workspace is removed, and abandons it when the lock is lost.

**Tech Stack:** Rust 2024 workspace (`flux-fs`, `flux-core`, `flux-platform`, `flux-cli`), `blake3`, `std::sync::mpsc`, FaultFs (`crates/flux-core/src/fault_fs.rs`) for tests, `cargo nextest`.

**Spec:** `docs/superpowers/specs/2026-10-12-cut-9f1-chunk-checkpoints-design.md` (decisions 1-15 and its "Plan 1 rulings"). Plan 1: `docs/superpowers/plans/2026-10-12-cut-9f1-primitives-and-wal.md`, merged at `97bd8d7`. Parent spec: `FLUX_FULL_UPDATED_SPEC_V16.md` s155-s165, s170, s174, s191.

## Owner decisions that shape this plan (2026-10-12)

1. **Scope is TREE operations only.** A tree has a workspace directory (`DEST/.flux/operations/<id>/`, `run/place.rs` `TreePlace::create`); a single-file operation has none (`FilePlace::workspace_path` returns `"adjacent/{id}"`, and V16 s18.1 and s119 give a single file no `wal/`). A single large file keeps recopying under `--resume` until a later cut settles its layout with a V16 amendment. This is a documented limit, not a defect of this plan.
2. **The WAL generation lives in the manifest, format version 4** (V16 s162: "The operation manifest records the current generation durably"). A format-3 prior is "created by an older version" and `--resume` refuses it with the existing `--restart` message (`prior.rs:177`), the rule cut 9a already applied to format 2.
3. **The sink reaches `stage_file` as a tenth parameter** (the owner's call; agy preferred a `StageHooks` struct, a style-level difference with the same call-site count).
4. **A WAL write failure is a STOP of the tree walk** (like `TargetLockBusy`), with a new code `WAL_WRITE_FAILED`, keeping the failing file's partial.

## Global Constraints

- Chunk size 1 MiB (`wal::CHUNK_SIZE`, `wal/mod.rs`). A file shorter than 64 MiB writes no checkpoints (decision 10); the constant is `CHECKPOINT_MIN_LEN = 64 << 20`, pinned by a test.
- WAL flush: 1 s after the FIRST pending record, or 64 MiB of completed ranges (`WalConfig::DEFAULT`, `wal/writer.rs:41-46`); channel capacity 64 (`CHANNEL_CAP`); a blocked sender retries every 10 ms and beats the heartbeat on each retry (`SEND_RETRY`).
- Under Normal durability a checkpoint is ADVISORY and is trusted only after digest validation (Ruling 1). Under Strict the writer syncs the partial through a duplicate handle before it appends (decision 6). Normal registers NO duplicate.
- `attempt_id` is the constant 1. `wal_format` is the merged `FORMAT_VERSION = 1`.
- A changed source or a missing partial discards that file's checkpoints and recopies it with a REPORTED reason; it is never a hard `RESUME_INVALID` (Ruling 2). A WAL that cannot be read at all recopies the affected files and reports why; it never aborts the run.
- Nothing is discarded silently: every discard names its file and its reason in the resume report (decision 12).

The repo gate before every commit: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo nextest run --workspace --no-fail-fast` (expected: `N tests run: N passed`). Push and read CI after every task (Windows-only failures surface only there).

## Review Focus

Failure modes the spec implies that no single task's happy path exercises, most likely first. Each has a named test in the task that owns the code.

1. **A partial LONGER than its checkpoints** (bytes written after the last flush, or garbage past it): everything past the proven offset is cut, never trusted. Task 5 `a_partial_longer_than_its_checkpoints_is_cut_to_the_proven_offset`; Task 7 `resume_truncates_garbage_past_the_last_checkpoint`.
2. **A damaged or unreadable WAL under `--resume`** (`WAL_CORRUPT`, an unsupported format, a segment whose identity is `Unavailable`): the affected files recopy and the report says why; the run does not abort. Task 8 `a_corrupt_wal_recopies_and_reports_instead_of_aborting`, `an_unavailable_segment_identity_recopies_and_reports`.
3. **A complete temporary from cut 9c's `NotRenamed` arm** (every chunk validates, the partial equals the file length): nothing is read past validation and the file continues through the normal tail (metadata, Strict sync, note, publication). Task 7 `a_fully_validated_partial_copies_nothing_and_still_publishes`.
4. **The source changes while a resumed file copies** (the step-7 recheck): the partial is discarded exactly as today, and its stale checkpoints cannot mix with the recopy (a `FILE_BEGIN` resets the file's range set). Task 7 `a_source_that_changes_during_a_resumed_copy_is_discarded`.
5. **A mismatch in the MIDDLE of the file** (a flipped byte in an early chunk of the partial): the resume offset is the end of the last chunk that matched on both sides, the chunk that failed is recopied from its already-read source bytes, and the report names the offset. Task 5 `a_mid_file_mismatch_resumes_at_the_end_of_the_last_matching_chunk`; Task 7 `resume_recopies_from_the_first_bad_chunk`.

  `carry` is the SOURCE bytes that `decide` already consumed from `source` and that the caller must write FIRST: at most `CHUNK_SIZE` of them (exactly `CHUNK_SIZE` for a mismatch inside a multi-chunk file, fewer only when the source ends inside that chunk). INVARIANT, for BOTH starts: `source` is positioned at `start_offset + carry.len()`, where `start_offset` is `0` for `Fresh` and `offset` for `Resume`; so a `Fresh` verdict that consumed a chunk (a mismatch at chunk 0) still hands those bytes back and the caller NEVER reopens or seeks the reader. This exists because the source reader is `Read` only (`fs.rs:135`): no seek. (Panel round 1 found the first draft lost the consumed bytes on `Fresh`.)
- Algorithm (spec decision 7, steps 2-4): (a) source gate: `state.begin.source_len == gate.len`, `source_mtime == gate.mtime`, `source_identity == gate.identity`, else `Fresh(Some(SourceChanged(which)))`; (b) partial gate: `partial_len == None` -> `Fresh(Some(PartialMissing))`; the number of chunks to try is `min(ceil(partial_len / CHUNK_SIZE), highest recorded chunk + 1)` and a chunk is tried only if its digest is recorded and the partial holds ALL of its bytes (a short last chunk counts only if `partial_len` reaches the source length); (c) per chunk in order: read the source chunk (up to `CHUNK_SIZE`, looping short reads) and the partial chunk, hash both with BLAKE3, compare each with the recorded digest; on a match advance, else stop. `beat` runs once per chunk (a terabyte of reads with the lease unrefreshed would look stale). A mismatch at chunk `k >= 1` yields `Verdict { start: Resume { offset: k * CHUNK_SIZE }, carry: <the source chunk just read>, discard: Some(MismatchAt(k * CHUNK_SIZE)) }`; a mismatch at chunk 0 yields `Verdict { start: Fresh, carry: <the source chunk just read>, discard: Some(MismatchAt(0)) }`; running out of recorded digests or partial bytes after `k >= 1` matched chunks yields `Resume { offset: k * CHUNK_SIZE }` with an empty `carry` (nothing was read past the matched prefix); with `k == 0` and nothing consumed it yields `Fresh` with an empty `carry`, whose `discard` is `None` when the WAL held no digest for the file, `PartialMissing` when `partial_len` is `None`, and `PartialShorter { kept: 0 }` when the partial holds no whole chunk. A partial shorter than the highest checkpoint keeps the chunks that fit and reports `PartialShorter { kept }`.

## Stand-downs

- REJECTED (panel round 2, `attempt_id` hardcoded to 1 in `FileSink::begin`): the spec fixes it. Spec design Non-goals: "retries and attempt isolation (section 225; `attempt_id` is a constant 1 until retries exist)" and decision 4: a `FILE_BEGIN` resets the file's range set "even though `attempt_id` is a constant".
