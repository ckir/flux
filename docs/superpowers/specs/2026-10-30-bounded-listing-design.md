# Bounded directory listings (cut 23): a fixed memory budget for directories of hundreds of millions of entries

Spec section 8.1 (`FLUX_FULL_UPDATED_SPEC_V16.md:931`, "Ordered discovery") makes sorted per-directory visit order the default and the spec's headline promises "bounded resident memory" (`FLUX_FULL_UPDATED_SPEC_V16.md:436`). Today three structures grow with the number of entries in ONE directory. This cut bounds all three. Status: APPROVED by the owner on 2026-10-30; section 6.3 AMENDED on 2026-10-31 at the owner's direction (a hybrid index, after the store benchmark of section 4.3) and panel-reviewed (rounds 7 to 11); constants, the tier 2 store backend, the two-thread build and the criteria RE-TUNED on 2026-10-31 after the hybrid benchmark (section 4.3, second paragraph), negotiated with the peer over three rounds and approved by the owner. The re-tuning has not had a panel review.

Evidence base: `docs/phase3-measurements.md` (cut 22 and the "Cut A" section), the peak-RSS runs of 2026-10-30 on `main` at `c286819` (section 4.2), and two agy consults whose briefs and replies are in `.clavity/seams/bounded-listing*.md` and `.clavity/scratch/agy-replies/`. Every behavioural statement below about existing code cites a line read at `c286819`.

## 1. Intent

An operator copies, verifies or resumes a tree in which a single directory holds hundreds of millions of entries. flux must do that inside a memory budget that does not depend on the entry count, and must keep what makes it trustworthy: sorted visit order (hardlink canonical members and `--resume` depend on it, section 8.1), a directory snapshot taken in one forward pass, no write into the destination during `--dry-run`, and no overwrite of an entry whose stored spelling differs from the planned name.

Why now: Cut A (PR #148) removed 480 of the 576 bytes per entry that a fresh full copy cost, and the cut-22 profile left the source listing as the dominant remaining term. The owner confirmed on 2026-10-30 that the scale is "hundreds of millions" and that the pre-existing and resumed destination case must be covered in the same cut.

## 2. Goals, non-goals, anti-goals

Goals
- G1. The source walk (`walk`, used by copy, `--dry-run`, `verify` and the destination sweep) holds a bounded number of entries of any directory in memory, and still yields them in byte order of `name.as_encoded_bytes()` (`walk.rs:166`).
- G2. A pre-existing or resumed destination directory costs bounded memory in `NameIndex`, with the same observable decisions as today: the stored spelling `resolve` returns (it keys the resume claim lookup, `tree.rs:1970`, and the replacement claim, `tree.rs:2241`), and the namespace-collision refusal (`owner`).
- G3. Every place that lists a USER directory only to filter its names costs bounded memory with identical answers: the several-source dry run (`multi.rs:249`, `multi.rs:372`, `multi.rs:383`), the single-source dry run's leftover scan of the lock's directory (`run/dry_prior.rs:139`), the single-file copy's scan of the target's directory (`prior.rs:127`, `scan_file`), and `flux cleanup`'s scan of the lock's directory (`cleanup/discover.rs:325`).
- G4. Memory, measured as the marginal peak-RSS slope between 1,000,000 and 2,000,000 entries, is at most 5 B per entry on every command in section 7.
- G5. No spill file survives the process: not after exit, panic or `SIGKILL` on Linux and macOS (the file is unlinked as soon as it is opened), and on Windows by `FILE_FLAG_DELETE_ON_CLOSE` (the OS closes the handle at process death; HYPOTHESIS, confirmed against Microsoft's documentation by the plan's first Windows task). After a power loss the filesystem's own recovery reclaims an unlinked file; on Windows a leftover would sit in the operation workspace's scratch directory, which the existing workspace cleanup removes.

Non-goals
- N1. No unordered discovery (section 8.2 of the spec stays a future option) and no change to any visit order.
- N2. No change to the `--json` objects, failure-line texts or exit codes. A new failure (the scratch location is unusable) gets a new line under an existing code.
- N3. The control-state listings (`prior.rs:54`, `state.rs:1060`, `cleanup/discover.rs:261`) are not touched: they list operation workspaces and the checkpoint-log directory, bounded by the number of operations (read at `c286819`). The listing at `cleanup/delete.rs:1330` is inside a test helper. There is no `--delete` or extraneous-entry mode in flux. CORRECTION made while writing the plan (2026-10-30): an earlier draft also put `run/dry_prior.rs:139`, `cleanup/discover.rs:325` and `prior.rs:127` here, on the strength of a peer's reply that called them bounded by lock debris; reading them showed each lists a directory the user owns (the lock's directory, or the target file's directory) and filters it, so they moved to G3 and structure D.
- N4. Speed is not a goal. Below the thresholds nothing changes; above them the run pays disk I/O, and the spec states the cost but does not set a throughput target (section 9).
- N5. The offset of up to about 10 MiB between a full copy and a dry run (section 4.2) is not a structure and gets no work.

Anti-goals (a failure even if every test passes)
- A1. Moving the cost from process memory into the page cache of a memory-backed temporary directory: a 10 GB spill on `tmpfs` is 10 GB of RAM.
- A2. A silently wrong overwrite on a destination whose folding rules flux does not know (ext4 casefold, NTFS, APFS normalisation).
- A3. A progress-less minutes-long pause that lets the lock heartbeat lapse.

## 3. Constraints

- C1. Order. `walk` yields a directory's entries sorted by `name.as_encoded_bytes()` and nothing else (`walk.rs:166`), depth first. A spilled directory yields the identical sequence.
- C2. Snapshot. The listing of a directory is taken in one forward pass when the directory is entered (`walk.rs:220`, `walk.rs:486`), before any child is visited. Repeated `getdents` passes are forbidden (`rewinddir` gives no snapshot guarantee). This constrains the WALK's listing, which a copy's decisions depend on; structure D's scans (6.4) are best-effort single reads of one directory that a copy does not depend on (`multi.rs:248` calls them best-effort).
- C3. `--dry-run` writes nothing into the destination. Its scratch goes where the dry run's hardlink index already goes: a temporary directory made on first use (`HardlinkSlot::deferred`, `hardlinks.rs:56`).
- C4. A copy's scratch lives in the operation workspace, as the hardlink index does (`hardlinks.rs:38-39`).
- C5. Descriptor budget. A deep tree must not hold a file descriptor per ancestor: `DEFAULT_MAX_DEPTH` is 256 (`walk.rs:22`), and a common soft limit is 1,024 descriptors.
- C6. The lock heartbeat (`Session::beat`, `run/session.rs:79`; `beat_and_guard`, `tree.rs:893`) must keep running while a long listing is ingested or merged.
- C7. `unsafe` stays where it is: `flux-core` has none today (`unsafe` appears only in `flux-platform`). The run file stores `name.as_encoded_bytes()` (so the order is the walk's order, `walk.rs:166`) and rebuilds a name without `from_encoded_bytes_unchecked`: on Unix with `OsStrExt::from_bytes`, on Windows by decoding the stored WTF-8 to UTF-16 units in a small safe decoder and `OsStringExt::from_wide` (my call). The `flux-fs` traits stay object-safe where they are today.

## 4. Current state

### 4.1 The three unbounded structures

A. Source listing. `walk_with` reads the root with `fs.read_dir(root)` and sorts the whole `Vec<DirEntry>` (`walk.rs:220`); every subdirectory is entered the same way (`walk.rs:486`). A `Frame` keeps `entries: std::vec::IntoIter<DirEntry>` (`walk.rs:109`). `FileSystem::read_dir` and `DirHandle::read_dir` return `Result<Vec<DirEntry>>` (`flux-fs/src/fs.rs:217`, `fs.rs:469`); `DirEntry` is `{ name: OsString, file_type: FileType }` (`fs.rs:47-50`). Consumers of `walk::walk_with`: `tree.rs:483` (copy and dry run), `verify.rs:179`, and `run/sweep.rs:80`, which walks the whole destination for `<name>.flux-partial.<prior-id>` leftovers inside a copy (so it runs under the lock). (`run/mod.rs:605` calls the copy-tree driver, a different `walk`.)

B. Destination name index. `NameIndex` (`names.rs`) holds `listing: BTreeSet<OsString>`, an identity `table: Option<HashMap<ObjectId, Vec<OsString>>>`, `owners`, `pending`, `learned`. For a pre-existing keyed directory `NameIndex::for_existing` lists it whole (`names.rs:111-115`); `resolve` consults the listing, then `metadata(planned)`, then an identity table that `build_table` fills by `stat`-ing every listing entry (`names.rs:171-199`); `record_publication` adds every published spelling to `listing`, `owners` and `pending` while the index is tracked (`names.rs:210-239`). Built at `root_state` (`tree.rs:1169`) and `enter_dir` (`tree.rs:1679`). A directory the run created is untracked since Cut A (`names.rs:218`).

D. Several-source dry run. `dry_create_preview` reads `dest.read_dir()` once (`multi.rs:249`) for two uses: `folds_ascii_case`, which also builds a `HashSet` of every name (`multi.rs:94`), and `broken_leftovers` over every root (`multi.rs:331-336`). `dry_fold` reads a holder's whole listing again (`multi.rs:372`, `multi.rs:383`). Three more filter-only scans of a user directory, found while writing the plan: `dry_lock` lists the lock's directory and keeps the `<lock>.broken.*` names (`run/dry_prior.rs:139-141`, through `broken_leftovers`, `dry_prior.rs:113-127`); `scan_file` lists the target file's directory and keeps the names that carry a record infix (`prior.rs:127-129`, then sorts and dedups the matches); `cleanup`'s lock discovery lists the lock's directory, sorts it, and keeps the `<lock>.broken.*` files (`cleanup/discover.rs:325-330`).

## 5. Approaches considered

Sequencing: the owner chose ONE cut for all three structures (2026-10-30), over three cuts. Agy had recommended splitting the cheap destination work from the walk work. The plan therefore orders the work inside the cut (section 10) and keeps the three structures separately gated.

A (source walk) - one sensible way. Rejected, with reason: an unsorted stream (breaks section 8.1; agy showed hardlink canonical anchors and `--resume` depend on order); a compact in-memory arena (still O(n)); repeated `getdents` passes with a low-water mark (O(n^2/N) syscalls, and no snapshot, C2). Chosen: spill and merge (external sort).

B (destination index) - three options:
1. Two tiers: an untracked index plus a per-name probe on a destination "proven" not to fold, an on-disk index otherwise. Rejected: the proof is a detector, and the detector cannot cover Unicode case, normalisation, per-directory case flags (ext4 `+F`), trailing dots or 8.3 aliases (agy, `multi.rs:85-113`). A false "does not fold" verdict is a silent overwrite under `Publish::Replace` (anti-goal A2).
2. One mechanism: below a size threshold the in-memory index unchanged, above it an on-disk index. No detector. This stays; what backs the on-disk index changed (option 4).
3. Merge-join of the sorted source stream against a sorted destination listing. Rejected: a folding destination's order differs from byte order, so colliding names are far apart.
4. A hybrid (chosen 2026-10-31, after section 4.3): option 2's threshold, with the on-disk index split into immutable sorted runs for the pre-existing listing (point lookups by binary search over a block index) and a small mutable store for this run's own publications (6.3). Replaces the first draft, a single mutable `redb`, which missed its ingest criterion. Not the same as option 3: lookups are by exact name and by identity, not by a merge in source order.

Agy's counter-proposal to key the on-disk index by `fold_key(name)` was rejected by both sides: it moves the detector into the key (the code avoids the destination's folding function by asking the destination for the identity of the planned name and mapping identity to spellings, `names.rs:131-171`).

## 6. Design

### 6.1 Scratch space (shared)

One `ScratchSpace` per run, created on first need, owning (a) one append/truncate run file for the walk (6.2) and (b) the destination index's files (6.3): a second file holding the final sorted runs of above-threshold directories, and one embedded `redb` store for this run's publications. Neither is ever named in a directory a later run could find:
- Location, in order: the `--scratch-dir PATH` option if given (on `copy`, `copy --dry-run` and `verify`); for a real copy, the operation workspace `DEST/.flux/operations/<id>/scratch/` (C4); for `--dry-run` and `verify`, a temporary directory made on first use (C3), like the dry run's hardlink index, taken from the system temporary directory unless that is `tmpfs`, then from the user cache directory (`$XDG_CACHE_HOME`, else `~/.cache`, on Windows `%LOCALAPPDATA%`), then refused with the `--scratch-dir` hint. Only a run that actually spills ever touches the location; small runs never create it (my call). On Windows the dry-run/verify scratch goes in a `flux-scratch` subdirectory of that location, and on start-up any file in it older than 24 hours is deleted (a file still open in a live process cannot be, harmlessly), so a power loss does not leave scratch behind for good (my call). Free space is not checked ahead of time: a directory spills when it is listed, before its children are copied, so an `ENOSPC` surfaces at the start of the work that needs the space, not hours into a run.
- The file is created, opened, and unlinked at once (`O_TMPFILE` where available, otherwise create then `unlink`; Windows: `FILE_FLAG_DELETE_ON_CLOSE`), so a crash leaves nothing (G5). The index file, the transient files of an index build (6.3) and the store's file are opened the same way.
- A scratch location on `tmpfs` (Linux only: `statfs` `f_type` of `tmpfs`, `0x01021994`, or `ramfs`, `0x858458f6`; other platforms make no check, and an overlay mounted over `tmpfs` reports the overlay's type and is not detected, an accepted boundary) is refused unless it was given explicitly by `--scratch-dir`: the run stops before spilling with a one-line error telling the operator to pass `--scratch-dir` (anti-goal A1). The operation workspace is on the destination filesystem and is not checked. My call; the owner may veto. Tests pass `--scratch-dir` explicitly (6.5).
- A write failure (`ENOSPC`, I/O) stops the whole run as an operation-level failure, never a per-entry one: a partly written run file means the listing is unknown, and continuing would copy a wrong subset.

### 6.2 Source walk: sorted spill and merge

Thresholds (constants in `walk.rs`; my calls, tuned by the plan's measurement task, never user-facing): `RUN_ENTRIES = 262_144` (about 21 MB at 80 B per entry, held only while a spilling directory is being read), `MERGE_FAN_IN = 384` (one merge pass for a directory of up to `MERGE_FAN_IN * RUN_ENTRIES` = 100,663,296 entries; measured in 4.3: a second pass costs 1.3x), `MERGE_BUFFER = 16 KiB` (384 buffers are 6 MiB per merge; measured in 4.3: the same build rate as 64 KiB and 48 MB less peak memory when two families merge at once), and a directory with at most `INLINE_ENTRIES = 8_192` entries is sorted in memory exactly as today. Every spill sort and every merge heap compares an 8-byte big-endian prefix of the key (the first 8 key bytes, zero-padded for a shorter key) before the key bytes themselves; this is an implementation requirement, not a tunable (measured in 4.3: without it the slice comparisons were about half of the build time).

Listing a directory (`list_sorted`, replacing both `sorted(fs.read_dir(..))` calls):
1. Drain the OS directory stream ONCE, in one forward pass, into a buffer. If the stream ends with at most `INLINE_ENTRIES` entries the directory is sorted in memory exactly as today and nothing else happens.
2. Otherwise the directory is SPILLED, even if it would fit in one run: whenever the buffer reaches `RUN_ENTRIES`, or the stream ends with more than `INLINE_ENTRIES` entries, the buffer is sorted by `name.as_encoded_bytes()` and written as one sorted run to the run file, and the buffer is cleared (so a directory of 8,193 entries is one run, read back through the merge reader). The resident listing is therefore at most `DEFAULT_MAX_DEPTH * INLINE_ENTRIES` entries across the whole stack (about 168 MB for the contrived 256-deep chain of full inline directories, a few MB for real trees) plus one transient `RUN_ENTRIES` buffer.
3. Runs of one directory occupy one contiguous region of the single run file. Frames are LIFO (depth first), so regions are stack-allocated. The region is owned by a `Listing` guard that records the region's start offset when the listing begins and `ftruncate`s the file back to it in `Drop`; the guard is dropped when the frame is popped AND when `list_sorted` fails before the frame was pushed (`walk.rs:485-494` drops it on the error path), so no failure orphans runs. If the `ftruncate` in `Drop` itself fails, the `ScratchSpace` marks itself poisoned, and EVERY later `read_at` and `write_at` on it (a suspended parent's open merge reader included, which never calls `list_sorted` again) returns a fatal scratch error instead of reading from a desynchronised offset. The guard lives in the frame's entry source: `list_sorted` holds it locally while it reads and spills, and on success moves it into the merge reader that becomes the frame's `entries` (an in-memory frame carries none). All I/O on the shared file is positional (`read_at`/`write_at`; Windows `seek_read`/`seek_write`) through a shared `&File` held by the walk, so an ancestor's open merge reader and a child's appends never contend for a cursor or a borrow.
4. If there are more than `MERGE_FAN_IN` runs, runs are merged in cascade passes of at most `MERGE_FAN_IN` into longer runs until at most `MERGE_FAN_IN` remain (300 million entries: ceil(300,000,000 / 262,144) = 1,145 runs; one cascade pass of 384-way merges leaves 3 runs, which the streaming merge of item 6 reads directly; up to 100,663,296 entries there is no cascade pass at all). Each pass reads each run through a `MERGE_BUFFER` buffer with `pread`.
5. Disk: initial runs and the first merge pass's outputs stay in the region until the frame is popped (no compaction, no hole punching), so the spill peaks at about twice the raw listing (about 20 GB for 300 million 24-byte names); the final merge streams and writes nothing. `walk` is consumed by one thread, which strict LIFO truncation relies on (the plan confirms it against `tree.rs:483` and `run/sweep.rs:80`).
6. The frame then yields entries by a streaming k-way merge over the remaining runs (a binary heap of at most `MERGE_FAN_IN` heads). `Frame.entries` becomes an enum: the in-memory `IntoIter` or the merge reader. The event sequence is identical in both cases.
7. Run record format (internal to the process, never persisted): `u16 name_len, u8 file_type, name bytes` (`as_encoded_bytes()`; a Windows name is at most 255 UTF-16 units, so at most 765 WTF-8 bytes, well inside `u16`). A name that does not fit is an operation-level scratch error, never a panic. A run file is process-internal: written and read by one process on one platform, so a Unix byte name is never decoded by the Windows WTF-8 path.
8. Ties: two entries with equal `as_encoded_bytes()` cannot occur in one directory; the merge is stable regardless.

Liveness and fatal errors (C6): `WalkOptions` gains an optional `tick: Option<&dyn Fn() -> Result<(), FsError>>` (`tree.rs` adapts `beat_and_guard`, which returns a `CopyError`, by keeping the `FsError` inside it); `list_sorted` calls it every `TICK_ENTRIES = 65_536` entries read, written or merged, and `NameIndex::for_dir` takes the same `tick` for its ingest (6.3). `tree.rs` wires it to `beat_and_guard`, and the destination sweep (`run/sweep.rs:80`, which runs inside a copy and so under the lock) gets the run's tick; `verify` holds no lock and passes `None`. A failed beat, a scratch write error and a scratch location error are FATAL: `WalkError` gains `fatal: bool`, set for exactly those causes, and every consumer aborts the operation on a fatal `WalkError` instead of reporting it and skipping the subtree as it does for an ordinary one (`tree.rs:1205-1210` today reports every `WalkError` and continues; that arm gains the abort, mapped to `CopyStep::Heartbeat` for a beat; `verify.rs:179` and `run/sweep.rs:80` likewise: neither has an abort path today, so each gains one. `verify.rs` `MergedSide::advance` (`verify.rs:276-286`) maps every `WalkError` to an unreadable-directory item and continues; it gains a `fatal: Option<FsError>` field that it sets while it ends its iteration, and the comparison loop in `verify_trees` checks both sides' `fatal` before it emits anything from an item, so an early-ended side cannot make the other side's remaining items look `Missing` or `Extra`; `verify` then returns the error as an operation-level error. `partials_under` (`run/sweep.rs:68-104`) pushes a `PartialKept` warning and continues, and `sweep_partials` returns no error; `partials_under` gains an `Option<FsError>` result for a fatal cause and `sweep_partials`/`Place::sweep` (`run/place.rs:495-506`) propagate it with `?`. `partials_under` has a second caller, the dry-run prior scan (`run/dry_prior.rs:173`, which today discards the "unlistable" flag): it gains the same fatal result and returns it as a dry-run error, because a dry run that cannot list its scratch must say so, not report "no partials". `dry_restart` therefore returns a `Result`, and its two callers (`run/mod.rs:1445` and `run/multi.rs:955`, preview closures that today take a bare `DryPrior`) propagate it out of the preview step. The exact signatures are the plan's. `WalkError` is re-exported (`lib.rs:40`) but used only inside `flux-core`, so adding a field breaks no outside crate.) Without this a lapsed heartbeat would be reported as one skipped directory and the copy would continue unlocked. Progress: at `-vv` one engine `tracing::debug!` line when a directory starts spilling ("listing N entries in M runs") and one per merge pass ("merge pass K of P, B bytes"), so a multi-minute cascade is visible; no new flag.

Errors: a `read_dir` stream error mid-listing is the same `WalkError` as today for that directory (`walk.rs:495`); the ancestor set stays balanced (`walk.rs:487-494`).

### 6.3 Destination index above the threshold

`NameIndex` gains a second representation chosen at construction by the listing size: `for_dir(fresh, listed)` streams the destination listing through a counter; up to `INDEX_INLINE = 8_192` names it builds today's in-memory index (everything below this threshold is unchanged, including the identity table), above it the hybrid form below. `fresh` still builds the untracked index of Cut A.

AMENDED 2026-10-31 at the owner's direction. The first draft backed the whole index with one mutable `redb` store. The benchmark of section 4.3 missed that draft's pre-registered ingest criterion, and a second consult with the peer (`.clavity/seams/bounded-listing-store-r1.md`, `-r2.md`) agreed on the split below. The reasons it holds: the work a pre-existing directory needs is point lookups only (`names.rs:137`, `:150`, `:158`, `:165`; there is no ordered scan), the bulk of the data is written once and never changes, and what changes (this run's publications) is bounded by the number of files the run copies, which is paced by the copy itself.

The hybrid form has two tiers. A lookup consults tier 2 first, then tier 1.

**Tier 1: immutable sorted runs, built once per directory in the single listing pass.** Up to three families of records, each a sorted run:
- `names`: the entry name, sorted by `as_encoded_bytes()`. Answers "is `planned` stored under exactly this spelling".
- `inodes` (Unix only): `(d_ino, name)` sorted by `d_ino` then name, filled in the same pass from the entry's `d_ino` with no `stat`; an entry whose `d_ino` is absent or 0 is not indexed. It is a CANDIDATE generator, never an authority. A lookup that yields more than `MAX_CANDIDATES = 16` names for one `d_ino` (FAT, FUSE and other filesystems that do not give unique inode numbers) is treated as no candidate and takes step 5.
- `identity` (built lazily, step 5 below): `(ObjectId, name)` sorted by `ObjectId`, the on-disk form of the in-memory `table`.

Building a family reuses the spill-and-sort engine of 6.2 (the same run record shape with a different key, the same `Thresholds`, the same `tick`): the single listing pass fills a `RUN_ENTRIES` buffer per family, which is sorted (prefix comparison, 6.2) and written once per family; when the listing pass ends, the two always-built families are FINISHED (cascade passes of at most `MERGE_FAN_IN` until ONE run per family remains, then the block packing below) on two threads, one per family, through the same shared `&File` with positional I/O (measured in 4.3: 1.1x alone, the step that lifts the prefix-sorted build to 1.6-1.9 M names/s). The listing pass itself stays on one thread, and so does `tick`: the `tick` closure (6.2, `&dyn Fn`) is not shared with the workers; the listing thread waits for the two workers by polling at a bounded interval (at most 250 ms between polls) and calls `tick` on EVERY poll, not on an entry-count cadence, so a worker stalled on I/O cannot delay a beat (the beat closure is already called once per copied entry today, `tree.rs:893-896`, and paces itself: `Session::beat` returns at once until its interval has passed, `run/session.rs:79-80`); the wait ends on the FIRST of: both workers finished, a `tick` error, or either worker's error or panic (seen when its join handle finishes); on any of the last two the listing thread sets a shared stop flag that both workers check at their own `TICK_ENTRIES` cadence, joins BOTH workers, and only then returns the first error (the `tick` error, or the failing worker's; a worker's panic payload is turned into the build's error, so `for_dir` returns `Err` and the listing thread never panics); a stopped sibling's partial output and a failed build's region are truncated by the frame's guard as for any failed build. A worker blocked in a kernel call cannot see the flag until the call returns, the same exposure the single-threaded listing has today. While a family is built the intermediate runs and each pass's output live in transient unlinked files that exist only during that build (nothing deeper on the stack is active then, so no ordering with other frames is needed); the single final run is written into a region of the run's shared INDEX FILE, which is stack-allocated and truncated by a `Listing`-style guard when the directory's frame is popped, exactly as 6.2 item 3 does for the walk (same poisoning rule). The index file is a second file of the `ScratchSpace`, so a deep tree holds a constant number of descriptors (C5).

The final run is read in place. Its records are packed into 4 KiB blocks and followed by a static multi-level block index in the same region (a packed B-tree: each level holds the first key of every block of the level below, and the top level is one block). A lookup reads one block per level with a positional read through a block cache of `INDEX_CACHE_BLOCKS = 256` blocks (1 MiB) shared by all directories, so resident memory does not depend on the entry count (a flat per-block key array in memory would be about 43 MB at 300 million names and is NOT the design). The cache is advisory: a miss costs a read, never a wrong answer.

Disk, estimated and NOT measured: a record is about 35 bytes (2 length, 1 type, the name, 8 for `d_ino`), so 300 million names are about 10 GB per family; while a family is built the runs and the pass's output coexist (about 20 GB), then only the final run (about 10 GB) stays; two families (`names`, `inodes`) are resident for a directory (about 20 GB), a third (`identity`) only if step 5 runs. The operator sees this at `-vv`: one `tracing::debug!` line per family built ("indexing N names: family F, M runs") and one per merge pass, as 6.2 does.

**Tier 2: mutable, one embedded `redb` store shared by all directories of the run.** It holds only what THIS run changes, so its size is bounded by the number of files the run publishes, never by the pre-existing listing. Keys are the 25-byte directory prefix then the datum: one tag byte (`0` Strong object identity, `1` frame ordinal) then `volume` as 8 and `index` as 16 big-endian bytes (for an ordinal, `volume` is 8 zero bytes and `index` is the `u64` ordinal zero-extended to a `u128`: 8 zero bytes then the ordinal big-endian), followed by the raw bytes of the datum with no separator, so no name or directory can collide with another by prefix. A directory's prefix range, used by every per-directory read and by `retain_in`, is the half-open byte range from the 25-byte prefix (inclusive) to its successor (exclusive), the successor being the prefix incremented as a 25-byte big-endian integer; it always exists because the tag byte is 0 or 1, so a prefix is never all `0xFF`. Tables:
- `names2`: `(dir, spelling) -> ()` for every spelling this run published into the directory (planned and stored).
- `owners`: `(dir, spelling) -> target` and `learned`: `(dir, spelling) -> seq`, the same two maps the in-memory index keeps, with the per-directory `next_seq` counter held in memory in the directory's index (one `u64`). `owner(&stored)` stays: two FILE roots at DEST's top level can alias on a folding volume (the documented boundary in `docs/accepted-boundaries.md`, the "two FILE roots that alias" entry); within one source's directories no two targets share a planned name (`plan_roots`, `roots.rs:86-135`: sources take distinct names and each folder root lands under its own `DEST/<name>`).
- `ids`: an overlay on the `identity` family that reproduces `Self::apply` (`names.rs:199-206`), which removes the WHOLE entry of a replaced object and then adds the published object's spellings. Rows are `(dir, ObjectId, spelling) -> seq` (spelling present) and `(dir, ObjectId, empty) -> seq` (a WIPE: the object's whole entry removed; a real name is never empty, so the key cannot collide), `seq` taken from a per-directory counter of its own, held in the directory's index and distinct from `learned`'s `next_seq` (`names.rs:80` starts that one at 0), whose FIRST row takes `seq` 1, so every wipe row has `seq >= 1`, larger than a run row's 0. EVERY publication whose identity is `Strong(id)` writes a spelling row for each spelling it published under `id`, a new file included (`names.rs:203-205` adds the spellings whether or not `replaced` is set); a publication that replaced an object writes a wipe row for the replaced object FIRST and the spelling rows after it, each row taking the next `seq`, so the wipe cannot mask the rows of the same publication (`names.rs:200-205` removes, then adds). A run row counts as `seq` 0; a spelling row counts only if no wipe row of the same object has a larger `seq`; a later write to the same key overwrites. This table REPLACES the in-memory index's `pending` list and its replay (`names.rs:192-194`): the overlay is applied at lookup time, so it does not matter whether a publication happened before or after the `identity` run was built (before: the stat pass already sees the new object and the wipe and spelling rows are redundant; after: the run still holds the old rows and the wipe masks them). Matching the in-memory index here, including that a wipe also removes the replaced object's OTHER spellings, is deliberate: the answers must be identical (G2).
There is no separate inode table for this run's publications: on Unix `id.index` IS the `d_ino`, so the `ids` spelling rows for `id` (a prefix range read over `(dir, id)`) are exactly the candidates a published entry contributes, with the `seq` the wipe rule needs (a table keyed by `d_ino` alone would hold the same spellings without the `seq`, and a replaced object's surviving spelling would escape the wipe; panel round 8 found this and the table is removed). A later alias of a name published by this run still finds a candidate without the stat pass. A stale candidate is harmless: every candidate is verified by identity (step 4).

Writes go through a write transaction that is committed with `Durability::Immediate` every `PUBLICATION_COMMIT = 1,024` publications and at the end; reads inside the run go through that transaction, so every lookup sees every earlier publication. `redb`'s `WriteTransaction::commit` takes the transaction by value, so each commit is followed at once by `begin_write` for a successor and the tables are opened again from it; the store wrapper owns that rotation and no caller holds a table across it. The commit mode matters for memory: `redb` keeps the bookkeeping of non-durable commits in memory until a durable one (`redb-4.4.0/src/tree_store/page_store/page_manager.rs:378-403`, cleared at `:1281` and `:1764`), which is how the section 4.3 benchmark's RSS grew; with periodic durable commits the resident part is the cache, set to `INDEX_STORE_CACHE = 16 MiB`. The store is opened through a `StorageBackend` of our own (`redb-4.4.0/src/db.rs:69-100`; `Database::builder().create_with_backend`, `db.rs:2182`) that delegates `len`, `read`, `set_len` and `write` to the scratch file and whose `sync_data` returns `Ok(())`: the store is an unlinked scratch no later run reads, so durability across a crash buys nothing, while the durable commit path still writes every dirty page and clears the non-durable bookkeeping (`page_manager.rs:1739-1764`), which is the property the memory argument needs (measured in 4.3: 3,500 to 25,473 rows/s on random keys, zero `fsync`/`fdatasync` under `strace`, `RssAnon` slope flat). A write error still surfaces through the backend's `write` and poisons the `ScratchSpace`; an `ENOSPC` the kernel reports only at writeback is not seen by this run, which is the same exposure the walk's run file has (its writes are not synced either). When a directory's index is dropped its rows are removed with `retain_in` over its prefix range in each table, so the file does not hold rows of directories already left. A failed write or commit marks the `ScratchSpace` poisoned (6.2 item 3), as in 6.6.

`resolve(planned)` above the threshold:
1. `planned` is in tier 2 `names2` or tier 1 `names` -> `metadata(planned)`; `Entry { stored: planned, meta }` (a vanished entry is the outer `NotFound`, as `names.rs:137-140` does today).
2. Else `metadata(planned)`: `NotFound` -> `Absent`; any other error propagates.
3. Found with a non-Strong identity -> `Ok(Err(NameError::Unresolvable))`, as `names.rs:146-148` does today (the outer `Err` stays reserved for an I/O failure).
4. Found with `Strong(id)` (Unix, `inodes` family present) -> candidates are the tier 1 `inodes[d_ino = id.index]` names, each counting as `seq` 0, and the tier 2 `ids` spelling rows for `id` with their `seq`; a candidate whose `seq` is smaller than the latest wipe row of `id` is DROPPED before verification (the `ids` rule above), so a replaced object's surviving hardlink spelling, met later under an alias, yields no candidate and the step answers `Unresolvable`, exactly as `names.rs:201` removes the whole entry and `names.rs:152` then refuses (G2; panel round 8 traced the divergence a wipe-blind step 4 had); each remaining candidate is VERIFIED with `metadata(candidate).identity == Strong(id)`; the verified candidates, deduplicated (the two tiers can name the same spelling, and `names.rs:58-69` keeps each spelling once, so `spellings.len() > 1` must count distinct names), are the spellings. The existing selection rule then applies unchanged, with `learned` and `owners` read from tier 2 (`names.rs:154-171`: the first publication-`stored` spelling, else the lexicographically smallest; several spellings are one entry only when this run wrote every one for the same target).
5. No verified candidate (or no `inodes` family on this platform) -> the `identity` family is built lazily, once per directory: every name of the `names` run is `stat`-ed in order (exactly what `build_table` does in memory today, `names.rs:178-199`, with `tick`; an entry that vanished is skipped, any other error propagates and the family is not built, as today), emitting `(ObjectId, name)` records through the same build as above. The spellings of the probed object are then `the identity-run rows for `id` and the `ids` spelling rows for `id`, keeping only those not wiped by a later wipe row (the rule in the `ids` table above)`, deduplicated, and the same selection rule as step 4 is applied (the `inodes` families are not consulted again). This is a DEPARTURE from the negotiated "fail closed with `Unresolvable`": same safety, no new refusal on Windows, overlayfs, NFS or btrfs subvolumes; the cost is time, paid only by a run that meets an alias in a directory above the threshold, and announced at `-vv`. A wrong `d_ino` therefore costs time, never a wrong overwrite. Completeness: the names of one object in one directory share one `st_ino`, hence one `d_ino`, so a `d_ino` that is wrong for one spelling is wrong for all of them and yields zero verified candidates (fallback), never a partial set (my argument; the plan adds a `FaultFs` case where `d_ino` is deliberately wrong, a case where a replacement was published BEFORE the `identity` family is built and one AFTER, one where a name is replaced and then replaced back, and one where the replaced object had a second spelling (the wipe removes it, as `names.rs:201` does), one where a NEW file (`replaced == None`) is published and then met under a case-folded alias on a platform with no `inodes` family (step 5 must resolve it from `ids`, as `names.rs:203-205` does), one where a publication's stored and planned spellings share a `d_ino` (both come back from `ids`), and one where the replaced object keeps a second hardlinked spelling on disk and is then met under an alias of that spelling (the wipe masks the tier 1 candidate; the answer is `Unresolvable` from step 4 AND from the in-memory index), to pin the overlay).

Windows and any platform whose listing carries no object id: the `inodes` family is absent and step 5 always applies. The stored-spelling call the peer suggested for Windows (`GetFileInformationByHandleEx`, a name-information class) is not used; it stays a possible later optimisation, unverified.

Mutation during the run: the destination is changed by this very run; tier 2 is updated at `record_publication` exactly where the in-memory index is today (`names.rs:210-239`). Tier 1 is never modified after it is built. External changes during the run were already a race (`names.rs:137-140`); the index does not widen it.

Store choice, and what was rejected. A single mutable store for all of it was the first design and is rejected on a measurement: `redb` ingest of random-order 49-byte keys ran at 32,137 to 34,730 names/s at 10 million names and 10,660 to 12,420 at 100 million (section 4.3), against a criterion of 100,000, which puts 300 million names at roughly 7 hours. The benchmark did not measure sorted-order ingest or durable commits, so redb fed sorted batches stays unmeasured; it was not chosen because it would add a sort of the whole listing in front of a database that then only holds the same data the sorted run already is (the peer's point, and the sort is needed anyway). Tier 2 stays `redb` because its load is bounded by the copy's own publication rate, which `redb` exceeds. The plan's measurement task decides on pre-registered criteria, and if either is missed the plan stops and returns to the owner with the numbers:
- Tier 1, at 10 million and 100 million names with both families built (the constants of 6.2 and the two-thread finish of 6.3): build rate at least 1,000,000 names/s (measured in 4.3: 1.57-1.93 M at 10M, 1.21-1.28 M at 100M); resident memory bounded by the formula of section 7 ("bounded-memory argument") evaluated with the chosen constants at BOTH sizes, and the `RssAnon` slope at most 1 B per entry (measured: 28.7-28.9 MB at both sizes). Lookups, measured at both sizes: for `names` probed in walk order (the production step 1 pattern, C1), median under 5 microseconds, p99 under 20 microseconds, and at most 0.05 block-cache misses per probe (measured: 1.4-1.5 us, 3.8-7.7 us, 0.0067); for `names` and `inodes` probed in random key order, at most 3 block-cache misses per probe (one read per level plus the data block, with the root always resident; measured: 2.15 and 2.41 at 100M). The random-probe latencies are REPORTED with the page-cache state and the device they ran on, not gated (measured: 219-263 us median and 1.2-1.6 ms p99 at 100M on this box's SATA SSD; 4-5 us at 10M, where the files sit in the page cache). Tier 2 point-lookup latencies are reported.
- Tier 2, at 10 million rows with `Durability::Immediate` every 1,024 inserts through the no-sync backend, random key order: sustained rate at least 5,000 inserts/s (measured: 25,473; ascending keys, the order of `names2`, `owners` and `learned`, 568,532), and the `RssAnon` slope between 5 and 10 million rows at most 1 B per row (measured: 0.02).

### 6.4 Filter-only scans of a user directory (structure D)

The three single-purpose filter scans (`dry_prior.rs:139`, `prior.rs:127`, `cleanup/discover.rs:325`) need no variant bookkeeping: each visits the directory once through the streaming read, applies its existing name filter inside the visitor, and keeps only the matches (the matches are then sorted, deduplicated or iterated exactly as today). Their answers are identical to today's for any directory. The rest of this section is the several-source dry run, whose fold probe needs two passes.

The several-source dry run's fold probe keeps its two-read design but makes the second read LAZY (revised twice while writing the plan: a single-pass bookkeeping of "variant classes" was tried and is WRONG, because an entry whose swapped spelling is absent injects a small key that evicts the real candidates' classes; panel round 1 of plan 1 gave a 24-name counterexample, `B1..B8`, `b1..b8`, `a1..a8`, reproduced here, and a single pass over an unbounded stream cannot know whether the swapped spelling of a LATE candidate was seen earlier without remembering every name). The answers stay identical to today's for any listing, which the plan proves against the old slice implementation kept as a test oracle (exhaustively over a small name universe and by a randomised comparison).
- Read 1 (always, one pass): keep (a) the `FOLD_CANDIDATES` smallest usable names (a bounded max-heap, as `folds_ascii_case` keeps today, `multi.rs:87-93`), and (b) for each root, the names that start with `<root>.flux-lock.broken.`, in stream order (`broken_leftovers`' filter, `dry_prior.rs:113-127`).
- The probe loop runs as today, candidate by candidate in ascending order, except that the listed-variant test (`multi.rs:97`, `present.contains(variant)`) is evaluated LAZILY. For candidate `c` with variant `v`: today's order is listed(`v`) then `F`; else `metadata(c)` not Ok-Strong then continue; else `metadata(v)`: Ok and the same Strong identity then `T`, Ok otherwise then continue, `NotFound` then `F`, any other error then continue. Run the metadata part first to an outcome `o`. If `o` is `F` (a `NotFound` variant), return `F`: a listed name is always found, so the listed test would have returned `F` as well. Otherwise (`o` is `T` or continue) the listed test could still turn it into `F`, so perform Read 2: one more streaming read of the directory that collects which of the (at most `FOLD_CANDIDATES`) variants are entries, stopping early once all are decided, cached for the rest of the loop; if `v` is listed return `F`, else `o`.
- Cost: a directory with no case twin (the ordinary, case-sensitive case) is read ONCE, because the first candidate's variant is `NotFound`. A folding directory, or one holding both spellings, is read twice; that is the only place the number of `read_dir` calls grows relative to today, and the existing fold-probe tests that pin `parent_listings` change by exactly one in those cases.
Memory is O(roots' leftover matches + `FOLD_CANDIDATES`). `dry_fold` over the holder (`multi.rs:372`, `multi.rs:383`) uses the same helper. The only value any caller uses is `== Some(true)` (`multi.rs:242`, `multi.rs:283`), but the plan's oracle compares the full `Option<bool>`.

### 6.5 Testing hooks

The thresholds (`INLINE_ENTRIES`, `RUN_ENTRIES`, `MERGE_FAN_IN`, `MERGE_BUFFER`, `INDEX_INLINE`, `MAX_CANDIDATES`, `TICK_ENTRIES`, `INDEX_CACHE_BLOCKS`, `INDEX_STORE_CACHE`, `PUBLICATION_COMMIT`) are fields of one `Thresholds` struct with a `Default` holding the production values and a constructor that refuses `INLINE_ENTRIES > RUN_ENTRIES` (a spilled directory must fill at least one run buffer); the walk, the index and `ScratchSpace` take it as a parameter, so unit tests use tiny values (for example 4, 8 and 2) and reach every spill, cascade and fallback path with a handful of names. Tests give `--scratch-dir` explicitly, which also bypasses the `tmpfs` refusal. Two assertions are mandatory in the unit tests: after a walk ends (normally or on an injected error) the run file's length is exactly zero; and a test binary with a counting global allocator (in its own test binary with one test, so no other thread's allocations are counted; the repository runs tests under nextest, one process per test) shows that, with `INLINE_ENTRIES = 4`, the spilled streaming merge performs a constant number of heap allocations per directory, not per entry (it guards against an implementation that quietly keeps names in memory). Three index tests are mandatory as well (panel round 9 found no listed test would fail if these rules were dropped): a `FaultFs` directory where `MAX_CANDIDATES + 1` entries with distinct identities share one `d_ino`, asserting that an alias probe makes no candidate `metadata` call in step 4 and takes step 5; a destination directory whose identity is NOT `Strong` (so its frame is keyed by an ordinal), asserting that its publications are recorded, resolved and removed under the ordinal prefix and that a sibling keyed by a Strong identity does not see them; and a parent and child directory that both record publications, asserting that popping the child and running its `retain_in` leaves every row of the parent in place. One integration test per structure runs the production defaults over a real 300,000-entry zero-byte directory on the CI runners (a few seconds) so the constants themselves are exercised.

### 6.6 Interfaces (contracts; names are the plan's)

- `flux-fs`: a streaming directory read on `FileSystem` and `DirHandle` that yields `DirEntry` values with an optional object index (`ino`) and does not collect them; the collecting `read_dir` stays for every caller outside this cut. `DirEntry` gains `ino: Option<u64>` (Unix `d_ino`, otherwise `None`); every literal of `DirEntry` in the workspace changes, and the compiler is the oracle for the list.
- `walk`: `WalkOptions { max_depth, mounts, tick, thresholds }`; a scratch handle passed to `walk_with` as a separate argument.
- `names`: `NameIndex::for_dir` gains the scratch handle, the directory it lists, the directory's key in the tier 2 store (its Strong object identity, else an ordinal the tree driver assigns to the destination frame: `for_dir` is called by `root_state` and `enter_dir`, `tree.rs:1169`, `tree.rs:1679`, not by `walk`) and the `tick`; its contract (`resolve`, `owner`, `record_publication`, `is_tracked`) is unchanged except that `owner` returns an owned `Option<FluxPathKey>` (`names.rs:119` returns a borrow `Option<&FluxPathKey>`, which a value read from the store cannot be); `record_publication` keeps its `()` return: a failed store write marks the `ScratchSpace` poisoned (6.2 item 3), so the next `resolve`, `owner` or write on it fails with the fatal scratch error and the run aborts rather than continuing on an index that missed a publication. A failed write on the LAST publication of a directory or of the run has no next call, so the final commit's result is returned as the fatal scratch error, and the poisoned flag is checked at the END of the `DirEnd` arm (`tree.rs:1362-1369`: after `flush_batch` has published the popped frame's last batch and after the frame's index has been dropped, since its drop runs `retain_in`, whose failure also poisons; a check at the `stack.pop()` itself would run before both writes) and at the run's finish, aborting when it is set; the two callers of `owner` compare with `is_some_and(|t| t != &target)` (`tree.rs:1953`, `tree.rs:3092`) and adapt trivially.
- CLI: `--scratch-dir PATH` on `copy` and `verify`; no memory-budget flag (the constants above are internal; my call).
- `FaultFs` (`crates/flux-core/src/fault_fs.rs`) implements the streaming read, an `ino` per entry (with a switch that makes `ino` wrong), and a fault hook for "the scratch write fails" so every failure row in section 8 has a test.

## 7. Acceptance gates

Written before any code, measured on the box in section 4.2, two or more runs each with the range quoted and the background load stated as uncontrolled (RSS is not timing; no wall-clock claim is made without the owner's go-ahead):
- GATE-A (walk): `--dry-run`, a fresh `copy`, and `verify` over the flat fixtures at 1,000,000 and 2,000,000 entries: marginal slope at most 5 B per entry; and the same over a `--dirs 1` fixture (every entry in one created subdirectory, so one nested frame holds them).
- GATE-B (destination): `copy` into a PRE-EXISTING destination holding the same names (resume over a finished copy, and overwrite of an old copy) at 1M and 2M: marginal slope at most 5 B per entry; the pre-change slope is measured first and recorded.
- GATE-D (filter-only scans): a DEST with 1M and 2M entries beside the roots under a several-source `--dry-run`, a single-source `--dry-run` whose lock sits beside a 1M and a 2M entry directory, and a single-file copy into a 1M and a 2M entry directory: marginal slope at most 5 B per entry for each.
- GATE-C (cascade): with the production constants a directory needs more than 384 * 262,144 = 100,663,296 entries before a cascade merge pass runs, which no fixture on this box reaches (GATE-X's 10 million entries make 39 runs). The cascade is therefore gated at library level: an integration test drives `walk_with` over a real directory of 2,000,000 zero-byte entries with `Thresholds { INLINE_ENTRIES: 512, RUN_ENTRIES: 4_096, MERGE_FAN_IN: 8, .. }` (488 runs, two cascade levels) and asserts, with a counting global allocator, that peak allocated bytes at 1,000,000 and at 2,000,000 entries differ by at most a fixed constant, and that the sequence equals the sorted names. The unit tests with tiny thresholds (6.5) cover the cascade's logic; this gate covers its memory at a size where a per-entry leak would show.
- GATE-X (scale): one `--dry-run` over a 10,000,000-entry flat fixture (about 220 MB of directory blocks; 31 million inodes free at the time of writing): peak RSS within 64 MiB of the 2M figure. My call; the plan may tighten it after measuring.
- Every gate on the walk (A, X) and on the destination index (B) quotes the number of directories that spilled (the `-vv` line), so a threshold that was never crossed cannot pass a gate; GATE-D, which spills nothing, quotes the number of `read_dir` calls instead (unchanged from today's) and the size of the leftover matches it kept; and the `RssAnon` marginal slope between 1M and 2M entries is reported and must be at most 1 B per entry (the 5 B figure alone could hide a small linear term).
- Stop rule: if a profile after the walk change shows another term that grows with the entry count (the plan's task 1 also profiles the residual), the plan stops and returns to the owner with the measured term; the gate is never loosened by me. `verify`'s pre-change slope is measured in task 1 as the baseline.
- Three-point scaling (500k, 1M, 2M) for each gate, so a fixed cache is not read as a leak and a small linear term is not hidden by the 5 B figure; for each, `RssAnon` and `RssFile` from `/proc/<pid>/smaps_rollup` are reported separately so memory moved into mapped file pages is visible (anti-gaming).
- A bounded-memory argument for 300M entries: peak resident memory at most `RUN_ENTRIES` entries per family being filled (each record plus its 16-byte sort entry; the walk's one family, or the destination index's two at once) OR `2 * MERGE_FAN_IN * MERGE_BUFFER` (12 MiB: two families merging at once), whichever is larger, because a frame's spill arenas are dropped before its merge begins (the two phases never coexist within one frame; a suspended ancestor frame holds only its merge reader's buffers, at most `MERGE_FAN_IN * MERGE_BUFFER` = 6 MiB each), plus `INDEX_CACHE_BLOCKS` blocks plus `INDEX_STORE_CACHE` plus the in-memory index of at most `DEFAULT_MAX_DEPTH * INDEX_INLINE` names, independent of the count (the criterion of 6.3 evaluates this formula with the constants and the implementation's record size and compares the measured peak RSS at 10M and 100M against it; the plan's measurement task states the evaluated number; measured 28.7-28.9 MB at both sizes with the benchmark's 40-byte records, whose spill term is 2 x 262,144 x 56 B = 29.4 MB and whose merge term is 12 MiB); and a disk estimate (about 20 GB of spill for the walk's 300M entries of 24-byte names, about 20 GB of final index runs for a 300M-entry destination directory's two always-built families, up to twice that while a family is being built, and about 10 GB more of final run plus its transient build runs if step 5 builds the `identity` family for that directory; estimates, not measured).
- Behaviour: the destination index above the threshold additionally passes a case where a name is replaced AFTER the lazy `identity` run was built (the run still holds the old rows and the `ids` wipe row masks them at lookup time; tier 1 is never modified) and one where it is replaced BEFORE (the later `stat` pass already sees the new object, and the `ids` rows are redundant with it; there is no `pending` replay above the threshold); for random name sets above the thresholds (including non-UTF-8 names, names holding every byte value except `/` and NUL, and names that sort differently as text and as bytes) the spilled sequence equals `sorted()` of the same set; the destination index above the threshold gives the same `resolve` and `owner` answers as the in-memory index on the same fixtures, including a case-folding `FaultFs` directory and two spellings of one object.

## 8. Failure semantics

| Failure | Result |
|---|---|
| scratch location unusable, `ENOSPC`, I/O error on a run write | operation-level failure; a one-line error naming the scratch location; no partial listing is ever used |
| scratch location is `tmpfs` and not given explicitly | refused before the first spill with the `--scratch-dir` hint |
| read error mid-listing of one directory | the same per-directory `WalkError` as today; ancestors balanced |
| lock heartbeat fails during a merge or ingest | the walk stops with the beat error, as a failed `beat_and_guard` stops a copy today |
| process killed | nothing remains: every scratch file was unlinked when opened (G5) |
| `d_ino` mismatch, no candidate verifies | the lazy identity table is built (6.3 step 5); never an overwrite and never a new refusal |
| `EMFILE` | cannot come from spill depth (a constant number of descriptors whatever the depth: the walk's run file, the index file and the redb store, 6.1; C5); a global `EMFILE` is today's failure |

## 9. Risks and open items

- R1. Tier 1's build rate (an external sort, twice per directory) and tier 2's commit-bound insert rate are MEASURED in a throwaway benchmark (4.3), not in `flux`: the plan's measurement task re-runs the criteria of 6.3 against the real implementation, and if it misses one the plan stops and returns to the owner with the numbers. A 300M-entry pre-existing directory pays the build once per run (about 4 minutes at the measured rate, two merge passes), and the cost is stated to the operator at `-vv`. A, D and the in-memory tier do not depend on that outcome. Still unmeasured: the order in which `ids` keys arrive in production (new files' `(dev, ino)`; the criterion uses random order, the slower case), the real `getdents` rate that feeds the build, and 16 KiB merge reads on a spinning disk (R4).
- R2. Windows has no object id in a listing, so a Windows alias in a directory above the threshold pays the lazy `stat` pass (6.3 step 5); that cost is stated, not measured. `FILE_FLAG_DELETE_ON_CLOSE` crash behaviour (G5) is a hypothesis confirmed by the plan's first Windows task.
- R3. `INLINE_ENTRIES`, `RUN_ENTRIES`, `INDEX_INLINE` are my starting values, not measured optima; `MERGE_FAN_IN` and `MERGE_BUFFER` were tuned in the 4.3 benchmark (384 and 16 KiB; 1,024 and a byte-budgeted dynamic fan-in were considered and rejected as 32 MiB of buffers or four times the read syscalls); the plan's tuning task adjusts the rest against GATE-A and GATE-B and records the ranges.
- R4. A spinning disk with a 384-way merge and 16 KiB buffers: sequential reads per run, one seek per buffer refill, four times the refills of 64 KiB buffers; acceptable on the SSD measured (the same rate as 64 KiB at 100M), not measured on a spinning disk.
- R5. Hardlinks: the canonical-member rule relies on sorted order (section 8.1); the behaviour test in section 7 includes a hardlink group straddling run boundaries.
- R6. This cut changes the compiled shape of `walk`, the `flux-fs` traits and `DirEntry`; every consumer and every `FaultFs` test fixture recompiles. The capstone range is large.
