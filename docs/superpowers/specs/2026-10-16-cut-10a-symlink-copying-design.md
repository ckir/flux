# Cut 10a: symlink copying (design)

Status: design for review. Against main `67091fc`. Every code citation below was read at that commit.

## 1. Why

`ROADMAP.md` lists "symlink copying" in the 0.1 scope and §25/§124 make `--links=copy` the default: a symlink is copied AS a symlink, its payload verbatim, never followed. Today the engine cannot create a link at all: every symlink in a tree is a failure (`TreeFailureCause::Symlink`, `crates/flux-core/src/tree.rs:179-181`, raised at `tree.rs:740-744`), rendered `SYMLINK_CREATION_UNAVAILABLE: <path>: a symlink is copied as a link (§25), which this version cannot create` (`crates/flux-cli/src/report.rs:15-16, 182-184`), exit 1. A tree with one symlink cannot be copied cleanly (`TODO.md:236-239`). The `FileSystem`/`DirHandle` traits (`crates/flux-fs/src/fs.rs`) have no operation that reads a link's payload or creates a link.

The next-cut fork was put to agy first (seam `.clavity/seams/next-cut-fork.md`, reply `.clavity/scratch/next-cut/r1-reply.md`, ALIGNED): it ranked this first, with §42 mount boundaries as a separate following cut, and the owner chose it (2026-10-16).

## 2. Goals, non-goals, anti-goals

Goals
- G1. A tree copy recreates every source symlink at the destination as a symlink with the identical payload, under `--links=copy` (the default), on Linux and macOS; on Windows where the process may create symlinks, and otherwise with the per-entry failure §127 prescribes.
- G2. `--links=skip` is implemented as §124 defines it: no link is created, each is reported as skipped, the run can still exit 0.
- G3. Every existing guarantee holds for link entries: handle-relative writes under `DEST` (§149.7), the claim protocol and `--resume`, the existing-destination policy (§5.1), the `.flux` reservation, and the lock/heartbeat stops.

Non-goals
- A symlink given as SOURCE (`flux copy link DEST`) stays refused before the engine (K7, `crates/flux-cli/src/resolve.rs:34-37`); its message no longer claims the version cannot create links (3.6). Copying a single link is a later cut (a `TODO.md` line is added at merge).
- `--links=follow` (§26): refused at parse as an unknown value. No link is ever followed, on either side.
- Hardlinked symlinks (§12.1): the walker has no hardlink topology yet, so every entry of a multiply-linked symlink inode becomes an independent symlink (what §12.1 prescribes for `--hardlinks=copy`). Recorded as a limitation, not a defect.
- Symlink metadata: timestamps and permissions of the LINK OBJECT are not preserved, under any `--preserve` option (decision D4; a deviation from §44.1's strictness, stated in `--help` and recorded in `TODO.md` at merge).
- Windows junctions and mount points as SOURCE entries are not recreated (D7). `flux verify` (§4.2) does not exist yet; payload comparison there is out of scope.
- No change to `walk.rs`: it already classifies every name-surrogate as `FileType::Symlink` and yields `WalkEvent::Symlink` (`crates/flux-core/src/walk.rs:260`).

Anti-goals (a failure even if every test passes)
- Any read, open or stat THROUGH a link on either side (§126): the source link's target is never opened; the destination link is never written through.
- A payload rewritten in any way (§125): not made relative, not made absolute, not re-rooted, not normalised, not re-encoded.
- A link silently replaced by a file, a junction or nothing (§127, §233.3): every link entry produces a created link, a skipped record, or a failure record.
- A write outside the directory handle (§149.7): no path-based destination call.

## 3. Design

A link entry is a file entry with no bytes. It goes through `copy_one`'s existing protocol (resolve the name, plan New or Replace, claim, publish, record) with the streaming steps replaced by one creation call; nothing new is invented for claims, resume, policies or reporting beyond what each subsection names.

### 3.1 The filesystem surface (`crates/flux-fs/src/fs.rs`)

```rust
/// A symlink's payload, read without following it (§125: verbatim bytes).
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Link {
    pub payload: std::ffi::OsString,
    pub kind: LinkKind,
}

/// What the link object itself says it points at. POSIX links carry no kind: `Unspecified`.
/// Windows links do (`FILE_ATTRIBUTE_DIRECTORY` is set on a directory symlink, dangling or not).
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum LinkKind { Unspecified, File, Dir }
```

`FileSystem` (the source side, by path, as `metadata(path)` is):
- `fn read_link(&self, path: &Path) -> Result<Link>`. Never follows. Refuses: a regular file or a directory at `path` with `Code::IoError`, kind `InvalidInput` (what `readlink(2)` itself answers, `EINVAL`, through `FsError::from_io`, `error.rs:106-120`; no separate stat is made, and no destination-side code is used for a source-side read); a name-surrogate that is not a symlink, which on Windows is a junction or a mounted-volume folder (`Code::SpecialFileUnsupported`); a missing path (`Code::IoError`, `NotFound`). The same three refusals for `DirHandle::read_link` below.

`DirHandle` (the destination side, relative to the handle, as every mutating method is):
- `fn create_symlink(&self, name: &OsStr, link: &Link) -> Result<()>`. Creates a symlink named `name` in the directory this handle holds, with `link.payload` as its payload, EXCLUSIVELY: MUST FAIL with `ErrorKind::AlreadyExists` if the name is taken by anything, a dangling link included, and never creates through a link (the same clause `create_new` carries, `fs.rs:255-275`). Calls `check_component(name)` first. Maps "this filesystem or this process cannot create a symlink" to `Code::SymlinkCreationUnavailable` (3.7); every other failure through `FsError::from_io`.
- `fn read_link(&self, name: &OsStr) -> Result<Link>`. As `FileSystem::read_link`, for a child of this handle. Used by the `--update` comparison and the resume check (3.3, 3.4).

Both existing implementors (`crates/flux-platform/src/dir_unix.rs`, `dir_windows.rs`, `std_fs.rs`) and the test fake (`crates/flux-core/src/fault_fs.rs`) implement all three. `FileType`, `Metadata`, `DirEntry` are unchanged.

### 3.2 The per-entry protocol (`tree.rs`, a new `link_one` beside `copy_one`)

For a `WalkEvent::Symlink { path }` under a live frame (`tree.rs:740`):

1. `out.files_total += 1` (as today). A reserved path (`reserved_path`, `tree.rs:785`) is refused exactly as a file's is (`CopyStep::Gate`, `reserved_conflict()`), before anything else.
2. `--links=skip`: `report(SymlinkSkipped)`; `out.symlinks_skipped += 1`; done. No source read, no destination touch.
3. Read the payload: `cx.fs.read_link(&src)`. `Code::SpecialFileUnsupported` (a junction) → `report(SpecialFileSkipped)`, `out.special_files_skipped += 1`, done (D7). Any other error is a failed entry: `CopyError::at(CopyStep::Source, e)` through `finish_copy` (step 6).
4. Resolve the name and plan, as `copy_one` does (`tree.rs:1093-1210`): `names.resolve` → `Absent` is `Plan::New`; an entry is `Plan::Replace { stored, meta }` after the same §241.5 owner check, the same `--resume` branch (3.4), the "destination is a directory" refusal, and the policy (3.3). The source LINK's own metadata is read here (`cx.fs.metadata(&src)`, a `symlink_metadata`, the walk event carries none) and the gate is the SAME function a file runs, `identity_gate(parent, name, &src_meta, opts.safety, publish)` (`copy.rs:289-337`): its every row, not one of them: the source-is-the-destination refusal, the `Weak`/`Unavailable` rows (refused under `--safety=strict`, otherwise `GateRead.degraded` carried into the `Outcome` so `finish_copy` counts `files_degraded` and records the warning, `tree.rs:2063-2066`), and the `NoReplace` refusal of an existing name. In the no-claim-store path (`tree.rs:1035-1055`, where `names` is empty) the gate's own `parent.metadata(name)` is the only destination read, as `copy_file_guarded` makes it.
5. Claim and publish, as `copy_one`'s `Plan::New` / `Plan::Replace` arms do, with the file's streaming replaced. The order of checks MIRRORS `stage_file` and `publish_staged` (`copy.rs:670-690`, `728-737`, `1084-1106`) and `discard` (`copy.rs:216-234`): every mutation is preceded by the heartbeat and the §99 guard, and a lost lock keeps the temporary as a leftover rather than removing it.
   - `temp = temp_name(name, &opts.operation_id)` (`copy.rs:253`, the same `<name>.flux-partial.<op>` name, so one sweep and one recovery rule cover links and files).
   - `beat()`, `guard()`. With entries pending AND something at `temp` (`parent.metadata(temp).is_ok()`, the probe `stage_into_batch` makes at `tree.rs:1464-1471`; nothing is flushed on a symlink whose temp name is free), the batch is flushed first: on a folding destination that object may be a pending sibling's temporary (the ASCII-only `folded()` pre-check, `tree.rs:498-500`, `1076-1083`, does not see a non-ASCII fold), and nothing at `temp` is ever removed while entries are pending. Then a leftover at `temp` under this operation's own id (a crashed earlier attempt under `--resume`) is removed as `stage_file` step 1 removes it (`copy.rs:676-682`, `remove_file`, which unlinks a link and refuses a directory). That the flush follows step 4's resolution and gate is the same order a file has: `names.resolve` (`tree.rs:1087`) precedes `stage_into_batch` (called from the plan arms, `tree.rs:1260`, `1366`); a sibling the flush publishes at a folding name is caught by the no-replace rename, as it is for a file, with the same `DESTINATION_NAMESPACE_COLLISION` whether the gate or the publish sees it (`tree.rs:2100-2104` maps both steps).
   - `beat()`, `guard()`, then the before-create hook (Replace: `insert_if_absent` of the `Existing` claim on `stored`, `tree.rs:1288-1310`), exactly `stage_file`'s step-3 order (`copy.rs:733-736`).
   - `parent.create_symlink(temp, &link)`. `AlreadyExists` with entries pending: flush the batch and create once more (the second backstop, `tree.rs:1509-1517`); otherwise, or a second time, it fails the entry (`CopyStep::Create`). Nothing of ours exists on a failed create.
   - identity of the created link: `parent.metadata(temp)?.identity` (judges the name, never follows; a link has its own identity, 3.7). A failure here discards the temporary (`discard`: `guard()` first, then `remove_file(temp)`; a lost lock keeps it as the leftover).
   - under Strict with a `prepared`-capable store: the note (`write_note`, `PreparedRecord { temp_name: temp, identity: identity_text(..), replacement, .. }`), exactly as a file's publish hook writes it.
   - `beat()`, `guard()` (`publish_staged`, `copy.rs:1089-1100`: a heartbeat failure discards the temporary; a lost lock KEEPS it, reported as the leftover with "kept: this run no longer holds the destination's lock", and, exactly as for a file, the shared `discard_note_on_failure` (`tree.rs`) discards the note on any publish `Err`, a lost lock included: a pre-existing behaviour recorded in the anomalies inbox, not changed by this cut), then the publish: `parent.rename_no_replace(temp, parent, name)` for New, `rename_replace` for Replace (`copy.rs:1102-1103`). A failed rename is discarded as a file's is (`guard()`, `remove_file(temp)`, the leftover rule when the removal fails) and the note is discarded (`discard_note_on_failure`).
   - record: `commit_prepared` (Strict) or `record_claim`/`upgrade_own_claim` (Normal), `ClaimNotRecorded` on failure, `names.record_publication(..)`, `files_overwritten += 1` for Replace. One addition, made INSIDE `record_claim` (`tree.rs:2035-2048`) so the file path's New arm (`tree.rs:1309`) gets it too: today it answers `Ok` to a present claim of the same target WITHOUT changing its status; it now upgrades a present own claim whose status is `Existing` when the record being written is `Created` (`upgrade_own_claim`), so a New publish that finds its own `Existing` claim (the name was absent at resolution but claimed by an earlier attempt: the Windows fallback's crash window below, or a destination entry the user removed between runs) leaves a claim that says `Created`, which the next `--resume` needs to resume it.
6. The result is a `Result<flux_fs::Outcome, CopyError>` handed to `finish_copy` (`tree.rs:2052-2110`), exactly as a file's is: `Outcome { bytes_copied: 0, metadata_failures: vec![], identity_degraded, published_identity, skipped: false }` on success (so `files_copied`, `files_degraded` and the warnings are counted there, D5), and on failure a `CopyError` with its `CopyStep` (`Source` for `read_link`, `Gate`, `Claim`, `Create`, `Publish`, `Heartbeat`) and `leftover`. That gives links, for free and without a second code path: the stops (`TargetLockBusy`, `Heartbeat`, `tree.rs:2083-2090`), the `NoReplacePublishUnavailable` stop and the `AlreadyExists`-at-publish → `DestinationNamespaceCollision` mapping (`tree.rs:2093-2104`), and the leftover collection in `run/mod.rs:384-388` (which reads `TreeFailureCause::Copy` only).

Link entries are never batched (`stage_into_batch` holds open writers and syncs them at a barrier; a link has neither), never checkpointed (no `FileCkpt`, no sink: `file_ckpt` is not consulted), and never resumed partially. They run the same aged/folded pre-check a file runs before resolving while a batch is pending (`tree.rs:1076-1083`) and the two backstops named in step 5, so ordering on a folding destination is unchanged. A directory with no claim store (a lockless copy, or an identity that cannot key claims, `tree.rs:1035-1055`) publishes the link as New with `Publish::NoReplace`, exactly as it publishes a file: an existing name is a collision.

### 3.3 Existing-destination policy (§5.1) for a link entry

| policy | existing entry at the name | result |
|---|---|---|
| `--overwrite` (default) | anything but a directory | `Plan::Replace` |
| `--update` | a symlink with the same `payload` and `kind` (`parent.read_link(stored)`) | skipped: `files_skipped += 1`, `bytes_skipped` unchanged |
| `--update` | anything else (a file, another link, an unreadable link) | `Plan::Replace` |
| `--skip-existing` | anything | skipped |
| any | a directory | refused, "the destination is a directory" (`tree.rs:1163-1170`) |

`update_replaces` (mtime and size) is not used for links: a link's size is its payload length on POSIX and 0 on Windows, and its times are not preserved (D4), so neither says anything. Payload equality is the comparison §4.2 names for links.

### 3.4 Claims, `--resume`, durability

- Claim records are unchanged (`ClaimRecord { target, status }`, `crates/flux-fs/src/claims.rs`): a link's claim is a claim. A later `--resume` finding a `Created` claim for this target at the stored name treats the entry as resumed when the destination is a symlink whose `read_link` equals the source's, `payload` AND `kind` (the one equality rule, shared with `--update`, 3.3; a claim store is never carried between platforms, so `kind` is `Unspecified` on both sides or set on both) (`files_resumed += 1`, `bytes_resumed` unchanged, and `names.record_publication(&target, Some(&stored), name, None, meta.identity)` exactly as the file branch does at `tree.rs:1150-1156`, so the rest of the directory's walk sees the name as this target's); otherwise it falls through to the policy and republishes (the same shape as `resumed_complete`, `tree.rs:1001-1015`, with that equality in place of length and mtime). A `parent.read_link(stored)` that fails (a junction at the name on Windows, an I/O error) is "not equal": it falls through to the policy, never fails the entry at this read.
- Note recovery (`run/recover.rs`, the T/D/R matrix at `decide`, `recover.rs:176-220`) compares identities and does not care what kind of object carries them, with ONE exception that this cut removes: the read of the temporary (`recover.rs:157-160`) accepts only `FileType::File` at the temp name and classifies anything else, a link included, as `uncertain(ANOTHER_OBJECT)`. So today a crash between `create_symlink(temp)` and the rename would leave the note undecidable: not committed, not discarded, the temporary kept. The cut changes that arm to accept `FileType::Symlink` as T too (its own identity, never its target's); a directory or any other type at the temp name stays `ANOTHER_OBJECT`. The removal side is ONE function: `remove_stray` (row 1's stray-temporary removal, `recover.rs:229-252`) checks the identity at the name and then delegates to `cleanup::artifacts::remove_validated` (`recover.rs:251`), which at `cleanup/artifacts.rs:80` accepts only `FileType::File` and refuses everything else as `SafetyRejected` ("a recorded artifact is not a regular file"); the same function deletes every recorded leftover: `cleanup_pending_artifacts` through `cleanup/delete.rs:493` (`finish_completed`) and the single-file place's own partial (`run/place.rs:756`). The cut changes `remove_validated` to accept `FileType::File | FileType::Symlink` at the LEAF (the components stay link-refusing, through `open_dir`; a directory leaf stays refused), so a link leftover that a failed publish recorded (3.2 step 6, `run/mod.rs:384-388`) is deleted by `flux cleanup` instead of failing it as `Kept` and leaving the workspace `COMPLETED_BUT_UNCLEAN`, and row 1's stray link is removed. `remove_file` unlinks the link, never what it points at, which is what makes the acceptance safe. The matrix is otherwise unchanged, and the identity check is what makes a link at T as safe to discard as a file: `remove_file` unlinks the link, never what it points at. A crash AFTER the rename and before the commit needs no change: D is read with `dir.metadata(&v.name)` whatever its type (`recover.rs:162-166`), row 1 commits it.
- A temporary link left at `<name>.flux-partial.<op>` by a crash between its creation and its rename is `Unreadable` to `plan_resume` (`open_existing` refuses a surrogate, `fs.rs:265-275`), so it can never be mistaken for a partial file. It is deleted by the same two sweeps that delete a partial file, and BOTH need one change: the J1 sweep shared by `--restart` and `flux cleanup` (`run/sweep.rs`, `sweep_partials`) walks `DEST` and today deletes only `WalkEvent::File` entries whose name is `<name>.flux-partial.<prior-id>` (`Ok(_) => continue` skips a `Symlink` event); it must treat a `WalkEvent::Symlink` whose name matches exactly as it treats a file (`remove_file` through the handle unlinks the link, never its target), with the same `check` before the deletion and the same `PartialKept` warning on failure. The temp probe on a pending batch (`tree.rs:1464-1471`, `parent.metadata(temp).is_ok()`) already sees a link at the temp name. Without the sweep change a crashed link temporary would survive every later run and `cleanup`, which §233.3's spirit (nothing silently left) and §24.4 forbid.
- Durability: a link has no bytes to sync. Under Strict the claim store syncs its commits as today; the copy path does not sync the directory after a file's rename either (`copy.rs:1102`, no `DirHandle::sync` call in `copy.rs` or `tree.rs`), so a link's publication is exactly as durable as a file's.

### 3.5 Outcome and reporting

- `TreeFailureCause::Symlink` and `FailureTally::symlink` are REMOVED: a link entry's failure is a `TreeFailureCause::Copy(CopyError)` (3.2 step 6), rendered by the existing `copy_line` as `<CODE>: <path>: <cause>[; temporary left at ..]` with the error's own code (`SYMLINK_CREATION_UNAVAILABLE` for an unavailable creation), and counted in `failures.copy`, so in `files_failed` and `errors`. `report.rs:85` becomes `out.failures.copy`; the fixed `SYMLINK_WHY` line (`report.rs:182-184`) goes with the variant. The CLI's K7 refusal keeps its own path (`report::pre_engine`, 3.6).
- New `TreeFailureCause::SymlinkSkipped` (not a failure, like `SpecialFileSkipped`): rendered `<path>: object_type=symlink action=skipped (--links=skip)` with no code (it is neither an error nor a warning; §124 names the fields, not a code). Counted in new `TreeOutcome::symlinks_skipped`, which the CLI adds into `files_skipped` beside `special_files_skipped` (`report.rs:78`).
- `FailureTally::count` stays exhaustive with no wildcard (`tree.rs:224-234`): the removed variant leaves it, the new one is named there and counts nothing.
- A created link is counted in `files_copied` (and `files_overwritten` when it replaced), with no bytes (D5). The §53 JSON report gets no new field; the text summary is unchanged.
- Per-record stderr lines are unchanged for everything that is not a link.

### 3.6 CLI (`crates/flux-cli/src/main.rs`)

- `--links=<copy|skip>` on `CopyArgs` (`value_enum`, default `copy`): "How a symlink in the tree is copied: `copy` recreates it as a link with the same payload (§125); `skip` creates nothing and reports it as skipped (§124). `follow` is not supported." `follow` is not a variant, so clap refuses it with exit 2.
- `CopyOptions` (`crates/flux-fs/src/options.rs`) gains `links: Links` (`enum Links { Copy, Skip }`), threaded as every other option is (`options()`, `main.rs:137`).
- `--links` joins the resume configuration: `state::Options` (`crates/flux-core/src/state.rs:76-123`) gains `links: String` (`"copy"`/`"skip"`), `Options::of` fills it, `state::validate` checks it with `one_of("links", .., &["copy", "skip"])` beside the others (`state.rs:562-566`), and `run::resume::validate` (`run/resume.rs:96-107`) compares it with the others, so `--resume` with a different `--links` than the prior operation is `INCOMPATIBLE_STATE` with the same "the operation runs with X, this run asks Y" message (`FLUX_FULL_UPDATED_SPEC_V16.md:1482`, acceptance test 70 at `:13326-13327`). Compatibility with a state written before this cut, which has no `links`, rests on two facts the plan must honour: `Options` is `#[serde(deny_unknown_fields)]` with no defaults (`state.rs:74-76`), so the field carries `#[serde(default = "copy")]` or the old state does not deserialize; and `resume.rs:56-68` refuses as `STATE_CORRUPT` any state whose stored `configuration_fingerprint` differs from `options.fingerprint()`, so `canonical_bytes` (`state.rs:115-122`, four `name=value` lines, no rule for growth) appends `links=skip\n` ONLY when the value is `skip` and nothing when it is `copy`: every existing state keeps its four-line hash bit for bit, and a `skip` operation gets a fingerprint no pre-cut state can carry. Test 4a pins both.
- `--help` for `--preserve-times`/`--preserve-permissions` says links are not covered (D4).
- The K7 refusal message (`report::SYMLINK_WHY`) changes to `a symlink SOURCE is not followed; copy its parent folder, or name its target` and keeps `SYMLINK_CREATION_UNAVAILABLE`'s exit path (unchanged behaviour, corrected wording).

### 3.7 Platform arms (`crates/flux-platform`)

POSIX (`dir_unix.rs`, `std_fs.rs`):
- `FileSystem::read_link`: `std::fs::read_link` on the path (`readlink(2)` never follows and answers `EINVAL` for a non-link, which `from_io` maps to `IoError`/`InvalidInput`, 3.1). `kind: Unspecified`.
- `DirHandle::read_link`: `rustix::fs::readlinkat(&self.0, name)`.
- `DirHandle::create_symlink`: `rustix::fs::symlinkat(payload, &self.0, name)`. `EEXIST` → `AlreadyExists` (the kind the engine branches on). `EPERM` → `Code::SymlinkCreationUnavailable` (a filesystem that cannot hold a symlink answers `EPERM` on Linux; to be measured on vfat during the plan, with `EACCES` kept as `PermissionDenied`). `ENAMETOOLONG` and the rest → `from_io`.
- A link's identity: `statat(.., SYMLINK_NOFOLLOW)` already gives the link's own `st_ino` (`dir_unix.rs:239-244`, `std_fs.rs:766-780`).

Windows (`dir_windows.rs`):
- Contract first, mechanism second. The contract is 3.1's: handle-relative, exclusive, never through a link, `SymlinkCreationUnavailable` when the process lacks the right.
- `kind` is read from the source link's own attributes (`FILE_ATTRIBUTE_DIRECTORY` on the reparse point; `read_link` reports `Dir` or `File`), so creation never resolves the payload. `Unspecified` reaching the Windows arm (a link read on POSIX in the same process, which cannot happen) creates a file link; stated in the doc comment.
- Error mapping (revised after the final review, ruling R15): `CreateSymbolicLinkW` failing with 87 (`ERROR_INVALID_PARAMETER`, an OS that does not know the unprivileged flag) is retried ONCE without the flag, as Rust std does, and the retry's error is mapped; 1314 (`ERROR_PRIVILEGE_NOT_HELD`) is `SymlinkCreationUnavailable` with the text `symlink creation needs Developer Mode or the SeCreateSymbolicLinkPrivilege right` (as the spec's §80 amendment asks, `FLUX_FULL_UPDATED_SPEC_V16.md:6105`); 50 (`ERROR_NOT_SUPPORTED`) and 1 (`ERROR_INVALID_FUNCTION`) are `SymlinkCreationUnavailable` with `the destination filesystem cannot hold a symlink`; 183/80 and 5-on-an-existing-name are `AlreadyExists`; anything else, a still-87 included, goes through `FsError::from_io`. On POSIX `EPERM` and `EOPNOTSUPP` are `SymlinkCreationUnavailable` with the filesystem text (unmeasured on vfat/exFAT/msdos).
- `read_link` refuses a reparse point whose tag is not `IO_REPARSE_TAG_SYMLINK` with `Code::SpecialFileUnsupported` (junction `IO_REPARSE_TAG_MOUNT_POINT`, and any other name-surrogate), using the tag the arm already reads (`reparse_tag_of`, `dir_windows.rs:1480`; `is_name_surrogate`, `:95`).
- The creation mechanism is decided by MEASUREMENT in the plan (the `verifying-platform-assumptions` skill), between two candidates, in this order of preference: (b) `CreateSymbolicLinkW` on `canonical_path()` joined with the temp name, with `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` (+ `SYMBOLIC_LINK_FLAG_DIRECTORY` for `Dir`), after re-checking the handle's identity against the object at that path: ONE kernel operation, so a crash leaves either nothing or the finished link, and it is the call Developer Mode is documented to unprivilege. It is the one path-based write the arm would make: a stated §149.7 residual, bounded by the identity re-check (anti-goal 4 and I3 carry the exception). (a) `NtCreateFile` relative to the directory handle at the temp name, `FILE_CREATE | FILE_OPEN_REPARSE_POINT` (+ `FILE_DIRECTORY_FILE` for `Dir`), then `FSCTL_SET_REPARSE_POINT` with a symlink reparse buffer (`SYMLINK_FLAG_RELATIVE` when the payload is relative, `\??\` on an absolute substitute name): handle-relative, but TWO operations, so a crash between them leaves a plain empty file or directory at the temp name, which the partial sweep (3.4) would not remove (a directory is never `remove_file`d); (a) is admissible only with that residue closed (the handle opened with `FILE_DELETE_ON_CLOSE` and the disposition cleared after the FSCTL succeeds, or the sweep removing an EMPTY directory at a partial name with `remove_dir`), and only if (b) fails the measurement. Whether the FSCTL honours Developer Mode or needs `SeCreateSymbolicLinkPrivilege` outright is the peer's reasoned claim, to be measured, not assumed. The measurements: which candidate succeeds in Developer Mode without elevation; which error each returns without the right (`ERROR_PRIVILEGE_NOT_HELD`, 1314, expected, mapped to `SymlinkCreationUnavailable`); what `read_link` returns for an absolute and a relative payload (verbatim round trip); and the two rename questions below. `ERROR_INVALID_FUNCTION`/`ERROR_NOT_SUPPORTED` from a filesystem without reparse points map to `SymlinkCreationUnavailable` too.

This keeps the trait's "still atomic" `rename_replace` contract, needs no engine change (the same arm serves `publish_staged` for ordinary file copies onto a user-made directory link and `link_one`), and a failing retry fails the entry with that status and loses nothing. Not yet measured (a follow-up owner probe, safe either way): a directory link replaced BY a directory link; a junction replaced by a file; ReFS, FAT32/exFAT and SMB (the retry is reached only after ACCESS_DENIED on a reparse-point target, so ordinary replacements never touch the new call).

## 5. Failure cases (state combinations)

| Event | Behaviour |
|---|---|
| `read_link` fails (I/O, permission) | `Copy(e)` record at `Source`, `files_failed`; next entry. |
| source entry is a junction (Windows) | `SpecialFileSkipped`; `special_files_skipped`; exit unaffected. |
| source or destination identity `Weak`/`Unavailable` | as a file: refused under `--safety=strict`, otherwise degraded and warned (`identity_gate`). |
| creation unavailable (privilege, filesystem) | `Copy(SymlinkCreationUnavailable)` at `Create`; nothing at the temp or final name; the Existing claim (Replace) stays, as a failed file's does; exit 1. |
| temp name occupied, batch empty | the leftover is removed under the guard before the create (a directory there fails the entry). |
| temp name occupied, batch pending | the batch is flushed first (never a removal while entries are pending), then the create; `AlreadyExists` at the create with entries pending flushes and retries once. |
| lock lost before the publish | the temporary is KEPT and reported as the leftover; the note is discarded as for a file (`discard_note_on_failure`; anomalies inbox) (as `publish_staged`). |
| rename fails | guarded discard of the temp; note discarded; `Copy(e)` at `Publish`; leftover reported if the removal failed; `AlreadyExists` becomes `DestinationNamespaceCollision`, a missing no-replace primitive stops the run. |
| Windows: a regular file replaces an existing directory link | the plain rename is denied (ACCESS_DENIED); the arm retries once with `FileRenameInformationEx` + POSIX semantics; success is atomic, a failing retry fails the entry with that status and the link is untouched. |
| destination name is a directory | refused, as for a file. |
| destination entry is this run's other target (§241.5) | `DestinationNamespaceCollision`, as for a file. |
| `--resume`: `Created` claim, same payload at the name | resumed, no write. |
| `--resume`: `Created` claim, different object at the name | republished under the policy. |
| lock lost / heartbeat fails at the entry | the run stops (`finish_copy`'s rule). |
| claim not recorded after publish | `ClaimNotRecorded`; the link stays published; counted as copied. |
| `--links=skip` | `SymlinkSkipped`; nothing read from the link; exit unaffected. |
| crash between `create_symlink(temp)` and the rename | a link at `<name>.flux-partial.<op>`; `--restart` and `cleanup` delete it (3.4); `--resume` finds no claim and republishes (the temp is removed and recreated). |
| a link at a reserved control path (`.flux/operations`, `.flux/standalone`, `.flux/atomic`, or below) | reserved-path refusal at `Gate`, before any read. A root-level `.flux` link is ordinary data exactly as a root `.flux` file is (`reserved_path(".flux")` is false by a pinned test); it follows the file rule. |
