# Bounded directory listings, plan 3 of 3: the hybrid destination index (structure B)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A pre-existing or resumed destination directory of any size costs bounded memory in `NameIndex`, with the same `resolve` and `owner` answers as the in-memory index (spec G2), and the memory stays bounded when this run publishes millions of files into one directory.

**Architecture:** Below `index_inline` (8,192) names nothing changes. Above it `NameIndex` takes a hybrid form: tier 1 is up to three immutable sorted families (`names`, `inodes`, lazily `identity`) built once per directory by plan 2's spill-and-merge engine, generalised to a fixed key in front of the name record, packed into blocks with a static block index, each family in its own lane of the `ScratchSpace` (owner ruling F1, 2026-11-02) so a deep tree holds a constant number of descriptors; tier 2 is one embedded `redb` store per run, opened over an unlinked scratch file through a backend whose `sync_data` does nothing, holding only this run's publications. An inline index whose maps reach `index_inline` migrates them once into tier 2 (owner ruling F4). The copy wires the index through `root_state` and `enter_dir`; a scratch or store failure poisons the space and aborts the run at the next index call or at the directory's end.

**Tech Stack:** Rust 2024 (`rust-version = "1.98.1"`), `redb` 4.4.0 (workspace dependency `redb = "4.3"`, `Cargo.lock` pins 4.4.0; new to `flux-core`), `std::thread::scope`, positional file I/O, `nextest`, `proptest`, `FaultFs`.

**Spec:** `docs/superpowers/specs/2026-10-30-bounded-listing-design.md`, sections 6.3, 6.5, 6.6, 6.7 (plan 2's amendments), 7 (GATE-B, the bounded-memory argument), 8, 9 (R1, R2). Plans 1 and 2 are merged (`main` at `60ccd8a`): `read_dir_each`/`DirEntry.ino` (`crates/flux-fs/src/fs.rs:48-57`, `:516-526`), `ScratchSpace`/`Region`/`Thresholds` (`crates/flux-core/src/scratch.rs`), the run record and merge (`crates/flux-core/src/spill.rs`), the walk's spill (`crates/flux-core/src/walk.rs:540-583`, `:726-767`).

## Rulings this plan rests on (owner, 2026-11-02, after an AGY-FIRST consult: `.clavity/seams/bounded-listing-plan3-forks.md`, `[VERDICT: ALIGNED - F1 O6, F2 O1, F3 a, F4 b]`)

1. **F1: one scratch lane per family.** Spec 6.3 names one shared index file written by two threads; the benchmark that produced the measured rates wrote each family to its own files (`.clavity/scratch/bounded-listing-hybrid/main.rs:596-632`), and two workers cannot share one append point when the packed size is unknown until packing ends. `ScratchSpace` therefore holds four lanes (walk, names, inodes, identity) plus the store's file: constant descriptors (C5), no copy, no pre-sizing.
2. **F2: `spill.rs` is generalised**, not duplicated: a record is K fixed key bytes (0, 8 or 24) then plan 2's name record; the walk is K = 0 and unchanged in behaviour. Plan 2's spill and walk tests plus GATE-C (`crates/flux-core/tests/walk_cascade_memory.rs`) are the regression oracle.
3. **F3: the 100M-name criteria of spec 6.3 are measured by feeding the real builder from a synthetic listing** (the box has about 31M inodes free, spec 7 GATE-X). Real directories stay measured at 300,000 (CI) and 2,000,000 (GATE-B). The measurement involves timing and runs only after the owner's separate go-ahead, at top level with nothing else running.
4. **F4: an index whose in-memory maps reach `index_inline` migrates them once into tier 2** under the directory's Strong identity or an ordinal. The code never lists a directory whose identity is not Strong (`tree.rs:1210`, `:1733-1736` pass `listed = None` when `claim_parent` is `None`), so without this rule the spec's "ordinal" case never occurs while publications still grow `listing`, `owners` and `learned` (`names.rs:232-235`) without bound.

Plan-level calls, open to the owner's veto (Task 8 amends the spec for each):
- **P1.** The migration of ruling 4 applies to EVERY inline tracked index (listed below the threshold or never listed), not only to the never-listed case: one code path, and a listed directory of 8,000 names plus 300M publications is the same problem.
- **P2.** Step 5's lazy `identity` build iterates the `names` family when there is one, else the directory's `names2` rows in pages (a migrated index has no tier 1); in both cases every name is `stat`-ed in order, as `build_table` does today (`names.rs:174-197`).
- **P3.** A failure while BUILDING a child's index is classified as the walk classifies a listing: a listing error of that directory skips the subtree as today (`tree.rs:1737-1741`, `TreeFailureCause::CreateDir`); a scratch, store or tick error is fatal and aborts the run (`CopyStep::Resolve`, or the stored tick error). The root's build error aborts as today (`tree.rs:1211`).
- **P4.** Tier 1's `inodes` family is built only when at least one listed entry carried `ino: Some(n)` with `n != 0`; with none (Windows, the fakes in `InoMode::Absent`) the family is absent and step 5 applies.
- **P5.** The block size is a `Thresholds` field (`index_block`, production 4,096 as spec 6.3 says) so unit tests reach several index levels with a few hundred names; a level entry carries at most `index_block / 8` key bytes (the CAPPED key) and the length of what it points at. A capped key orders frames only up to its length, so the lookup descends to the first frame that can hold the target and scans FORWARD through contiguous frames until a record above the target; with the production cap of 512 bytes two distinct names of at most 255 bytes never share a capped key, so one block per level and one frame are read, and the forward scan is the correctness guard for longer names and for the 16-byte cap the tests use.
- **P6.** The store's rows of a finished directory are removed by an explicit `retire(tick)` at the directory's end, in batches of `publication_commit` rows with a tick between batches (the heartbeat interval is 5 s, `run/mod.rs:111`, and a directory can hold millions of publications); `Drop` only truncates the lanes. Rows left behind by an aborted run sit in an unlinked file and cost disk until the process ends, never memory.
