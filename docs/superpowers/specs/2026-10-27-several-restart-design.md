# `flux copy --restart` (and `--break-lock`) with several sources - design (cut 17)

Status: approved by the owner 2026-10-27; design panel GREEN at d2246b55c71c52bb0655293dd30aeb3606542ba2. Author calls are marked **(call)**. Owner decisions are marked **(owner)**.
Builds on `docs/superpowers/specs/2026-10-22-several-sources-design.md` (cut 11c; N1 and L1 there) and spec section 21.1.

## 1. Intent and why

`flux copy a b c DEST` refuses `--restart`, `--break-lock`, `--resume` and `--dry-run` today (`crates/flux-cli/src/main.rs:646-662`,
`several_flag_gate`). After an aborted several-source run the operator's only way out is `flux cleanup --force DEST` or a one-source
`flux copy --restart` (`TODO.md:1134`, L1). This cut lets `--restart` supersede an aborted several-source run, so one command both
clears the old run and copies again, exactly as it does for one source.

**(owner)** `--restart` must work immediately after a crash. Measured basis: a copy run's lock acquisition has no lease wait. A crashed
run's lock is `Dead` (OS lock released, workspace present) and `obtain` recovers it at once (`crates/flux-core/src/lock/obtain.rs`, the
`Classified::Dead` arm of `obtain`); the lease threshold exists only in `obtain_cleanup_lock` (same file), which is why
`flux cleanup --force` waits about 30 seconds (`TODO.md:1138`). A crashed several-source run's prefix lock records `workspace_path = none`
and classifies `Dead` too (`crates/flux-core/src/lock/site.rs:150-156`, where a `none` workspace is `Trusted`; pinned for a cleanup lock by `classify.rs:215`; several-sources design ruling R7).

What "immediately" covers **(call)**: every crash of a copy run after its destination lock record is written (the record follows `place.create`; a crash between the state's creation and the record leaves an empty lock, which `--restart --break-lock` takes over). `remove_own` rewrites the lock record to `none` BEFORE it retires the workspace (`crates/flux-core/src/run/mod.rs:1182-1186`), so a crash at any point leaves either a record naming a present workspace (`Dead`) or a `none` record (`Dead`); an `Orphan` (a record naming a missing workspace) arises only from outside interference and stays refused with `orphan_refusal` as for one source. One window is different: a crash between a prefix lock's `create_lock` and its `write_record` (`crates/flux-core/src/run/prefix.rs:108-123`) leaves an EMPTY prefix lock file, and because the destination record is written after `place.create`, an empty destination lock too; no prior workspace exists yet. The operator then needs `--restart --break-lock` for the destination lock and, under P1 (N2), removes the prefix file by hand; the refusal text of 3.4 says so.

## 2. Goals, non-goals, anti-goals

Goals
- G1. `flux copy --restart a b c DEST` supersedes every resumable prior at DEST (a several-source prior, a one-source tree prior, or both), then runs as a fresh several-source copy.
- G2. `--break-lock` is accepted with `--restart` and several sources and applies to the destination lock, as for one source (spec 240.5).
- G3. Every text that today sends the operator to `flux cleanup --force` for an aborted several-source run says `--restart` instead: the two arms of `resumable_refusal` (`crates/flux-core/src/prior.rs:180-224`), the checkpoint-write abort hint `abort_hint_lines` (`crates/flux-cli/src/report.rs:933-945`, with its doc comment at `:929-931`, pinned at `report.rs:1848-1851`), and the `several_flag_gate` hint (`main.rs:657-660`), which is deleted with its `--restart` arm (3.1). Their pinning tests (`prior.rs:633-656`, `report.rs:1848-1851`, `crates/flux-cli/tests/several_sources.rs:150-176`, whose assertion at `:170-174` ties the cleanup hint to `--restart`) change with them.
- G4. One-source commands behave exactly as today. State format 5 and format 4 are unchanged byte for byte.

Non-goals (each stays in `TODO.md`)
- N1. `--resume` and `--dry-run` with several sources (later cuts, in the order agy and the owner chose: dry-run, then resume).
- N2. `--break-lock` for the prefix locks (**owner**, P1): an unreadable prefix lock is refused with an honest message. P2 (take over and record each prefix takeover) is its own later cut because `state.takeover` is one optional slot (`crates/flux-core/src/state.rs:369`, `deny_unknown_fields`) and widening it risks a format 6 against several-sources goal G5.
- N3. Any change to the lease rule or to `flux cleanup`.
- N4. `--restart` with `--dry-run` for several sources (it stays the `--dry-run` usage error).
  Update 2026-10-28: cut 18 built `--dry-run` for several sources, with and without `--restart`, `docs/superpowers/specs/2026-10-28-several-dry-run-design.md`; N1 and N4 are closed for `--dry-run`, `--resume` remains.

Anti-goals (a failure even if the tests pass)
- A1. A restart that releases this run's own prefix locks while it supersedes a prior (the defect at `multi.rs:300-309`, see 3.2): the copy would then run with no namespace guard.
- A2. A message that promises `--break-lock` where `--break-lock` cannot help.
- A3. Superseding a live run: `--restart` still refuses `TARGET_LOCK_BUSY` when another run holds the destination or a prefix lock.
- A4. Any residue beyond the stale prefix lock files of L6 (3.3) that a one-source restart over the same prior would not also leave.

## 3. Design

### 3.1 CLI (`crates/flux-cli/src/main.rs`)
- `several_flag_gate` keeps `--resume` and `--dry-run` and loses `--restart` and its "run flux cleanup --force" hint. The `--resume` message gains "; run again with --restart to supersede an aborted several-source run", because `--restart` is now the way out that `--resume` is not. With `--restart --dry-run` the `--dry-run` message is the one printed.
- `--break-lock` already `requires = "restart"` (`main.rs:158`), so it is accepted exactly when `--restart` is.
- The `Copy` doc comment at `main.rs:39` and the `--restart` and `--break-lock` help are rewritten: several sources now work with `--restart` and `--break-lock`; `--resume` and `--dry-run` need one source; the `--break-lock` help (`main.rs:157`) says it takes over the DESTINATION lock, not a prefix lock.

### 3.2 Engine: `MultiPlace::remove` (`crates/flux-core/src/run/multi.rs:300-309`)
Today `remove(id)` releases this run's prefix locks (`release_cell(&self.prefix)`) whatever `id` is. `supersede` (`crates/flux-core/src/run/restart.rs:41-46`) calls `place.remove(&prior.state.operation_id)` for each superseded prior, so a restart would drop this run's prefix locks before any file is copied (A1). Fix: `remove(id)` releases the prefix locks only when `id` equals this run's operation id (`self.prefix_id.operation_id`); for any other id it only retires that workspace through `self.tree.remove(id)`. **(call)** The comparison lives inside `MultiPlace::remove` so the `Place` trait does not change. The `debug_assert!(!cfg.restart && !cfg.resume, ..)` at `multi.rs:443-446` is narrowed to `!cfg.resume`, and its comment is rewritten.

### 3.3 Order of a several-source restart (no new machinery)
`open_operation` (`crates/flux-core/src/run/session.rs`) already does: obtain the destination lock (`Dead` prior lock recovered, or taken over under `--break-lock`); `place.scan` (every resumable tree-kind prior of any format; `scan_tree` refuses a non-tree manifest in `operations` as corrupt, `prior.rs:97-101`); `place.create` (for several sources this acquires the prefix locks, recovering dead leftovers of names this run uses, then writes this run's state); write this run's record; `supersede` (set each prior ABANDONED with `superseded_by`, sweep partials, retire each prior workspace). Verified, not changed: `sweep_partials` walks DEST for `<name>.flux-partial.<id>` without reading the prior's roots (`crates/flux-core/src/run/sweep.rs`, `TreePlace::sweep` at `run/place.rs:495`), so it works for a several-root prior; `MultiPlace::sweep` delegates to it (`multi.rs:291`). A dead prefix lock of a name this run does not use stays as a stale file (several-sources limitation L6). A one-source tree restart over a several-source prior leaves ALL of the prior's prefix lock files, because `TreePlace::remove` only retires the workspace (`run/place.rs:519-521`); a several-source restart leaves only the names it does not reuse. **(call)** This cut accepts that: `supersede`, `sweep` and `remove` keep touching only the prior's workspace and partials, because clearing prefix locks is a new engine step on the lock path with its own ownership questions. It is to be logged in `TODO.md` as a follow-up together with the nested one-source-prior case of the Stand-downs (there is no L6 entry there today; 3.7 adds both). A later run that uses the name recovers the lock, and `flux cleanup` does not touch it.

### 3.3a Safety order under `--restart`
Spec 21.1 steps are unchanged: `still_owned` is checked before every mutation in `supersede` (`checked(locked)`), and a lost lock stops the run (`S21_1_s3_refuse_close`).

### 3.4 `--break-lock` and the prefix locks (owner, P1)
`PrefixLocks::take` (`crates/flux-core/src/run/prefix.rs:108`) keeps `Mode::Plain`, so `Obtained::Claimed` stays unreachable there. The destination lock takeover is unchanged: `open_operation` computes `mode` from `cfg.break_lock` (`session.rs:133`) and records `state.takeover` (`session.rs:~272`). When `obtain` returns `TARGET_LOCK_UNCERTAIN` for a PREFIX lock, its detail today says "run again with --restart --break-lock" (`uncertain_refusal`, `crates/flux-core/src/lock/obtain.rs`), which cannot help. The seam **(call)**: `PrefixRefusal::Lock` (`prefix.rs:44-51`) gains the failing name, `Lock { name: OsString, error: LockError }` (every site supplies it: the two `map_err(PrefixRefusal::Lock)` at `prefix.rs:104` and `:107`, the three constructions in `take`, and the test patterns at `prefix.rs:229, 243, 260, 298`), because `take` has no shown DEST path (`prefix.rs:97-103`) and `acquire` does not say which name failed; `MultiPlace::prefix_error` (`multi.rs:130-143`), which already maps the refusal and owns `lock_path(name)` (`multi.rs:93-97`), rewrites the detail when `error` is `Refused` with code `TARGET_LOCK_UNCERTAIN`, keeping the code, and passes `self.lock_path(&name)` (not `dest_shown`) as the path to `from_lock` for EVERY `Lock` refusal (Busy, Untrusted, Foreign, I/O too, whose path prefix therefore changes from DEST to the lock file; the existing prefix tests pin only the code, `multi.rs:1541`), because `from_lock` prepends `path.display()` to the detail at the lock step (`session.rs:500-505`); the detail itself therefore carries no path, so the file is named exactly once. `uncertain_refusal` passes no holder (`obtain.rs:98`), so only the code is kept. **(folded from panel round 4)** The same arm handles the sibling code `ARTIFACT_OWNERSHIP_UNCERTAIN`: for a prefix lock, `orphan_refusal` (`obtain.rs:83-91`) appends "flux cleanup DEST removes a dead owner's lock whose workspace is gone", which is false for a prefix lock (3.3). It is reachable today without this cut: a one-source copy into `DEST/<name>` crashes, its lock `DEST/<name>.flux-lock` names `operations/<id>` under `DEST/<name>` (`site.rs:159-161`, `operation_dir_exists` at `:178-198`), the operator removes `DEST/<name>`, and the next several-source run that uses `<name>` meets `Orphan` (`classify.rs:59-61`). `prefix_error` keeps `UNTRUSTED_DETAIL` (a private const at `obtain.rs:61`, which already says "inspect it, and remove it by hand if it is not needed"; **(call)** it becomes `pub(crate)` so the rewrite reuses the text instead of stripping a suffix by string) and drops the cleanup suffix; Orphan and Untrusted share the code (`obtain.rs:79, 92`) and the same honest advice, so keying on the code is exact. T4c pins it. Under `Mode::Plain` the only source of that code is `uncertain_refusal` (`lock/obtain.rs:96-104`, reached at `:131`; `give_up`'s torn-unheld arm is `BreakLock`-only, `:134`), so keying on the code is exact. The message then reads `<DEST>/<name>.flux-lock: this prefix lock has an unreadable record; if no Flux run is active on this destination, remove that file and run again with the same flags` **(call: exact wording of the detail is the builder's, but the path comes from `from_lock` only, the detail must say "the same flags", and it must not contain "--break-lock")**. A prefix lock left readable by a crash is `Dead` and needs no flag. The refusal applies only to a prefix lock of a name THIS run uses, because only those are acquired; an unreadable prefix lock of a name this run does not use is never opened. `--restart --break-lock` with an unreadable destination lock and an unreadable prefix lock CLAIMS the destination lock (`obtain` in `BreakLock` mode returns `Obtained::Claimed` after steps 1-5 of 240.5, `take_over` at `lock/takeover.rs:51-94`), then refuses at the prefix lock inside `place.create`; `give_back` lets a claimed lock go untouched (`session.rs:365-367`) and the step-6 overwrite that would record the takeover runs only after `place.create` (`session.rs:262`). So nothing is written: the destination lock file is byte-for-byte as before, `state.takeover` is never written, no workspace of this run exists. The rerun with the same flags claims it again. The CLI prints no extra warning.

### 3.5 Messages that name `flux cleanup --force` for a several-source prior
`resumable_refusal` (`crates/flux-core/src/prior.rs:180-224`): the one-prior several-source arm and the several-prior arm's suffix are rewritten to say `--restart` supersedes it, keeping the "(its partials and its recorded progress are deleted)" notice the other arms carry; its pinning test is `a_version_5_prior_says_to_run_cleanup_force_not_resume_or_restart` (`prior.rs:633-656`), renamed and rewritten with it. **(call)** A several-source prior may be superseded by any `--restart` whose scan reads DEST's `operations` directory: a several-source run or a one-source TREE run. A one-source FILE copy scans only the adjacent `<target>.flux-state.<id>` records (`TreePlace::scan` at `run/place.rs:474`, `FilePlace::scan` at `:712` via `scan_file`, `prior.rs:120`), so it never sees a several-source prior and its messages do not change. `--resume` still cannot continue a several-source prior. `--help` mentions cleanup nowhere today, and this cut adds no cleanup hint.

### 3.6 Reporting
No new flag, report field or JSON key. A restart reports as a one-source restart does today.

### 3.7 Documentation

The other files are `docs/accepted-boundaries.md:106` (its L1 text says `--restart` is refused with several sources), the `--help` texts, `TODO.md` L1 (close the `--restart` and `--break-lock` part, keep `--resume` and `--dry-run`), `ROADMAP.md` where it lists several sources, and `docs/superpowers/specs/2026-10-22-several-sources-design.md` (a dated note under N1 and L1, not a rewrite).

## 4. Approaches considered
- **A. Narrow engine fix (chosen; agy and the author agree).** Lift the CLI refusal, make `MultiPlace::remove` id-aware, keep `--break-lock` on the destination lock, fix the messages. About one cut (agy's estimate, 350-450 lines, unmeasured).
- **B. Restart as "cleanup, then fresh run" inside the CLI.** Rejected: two steps that are not atomic, it drops the ABANDONED and `superseded_by` record and the `still_owned` checks of 21.1, and it would inherit cleanup's lease wait, which the owner ruled out.
- **C. Split `--break-lock` from `--restart`.** Rejected: the CLI requires `--restart` for it (`main.rs:158`) and 21.1 couples them.
- **Break-lock reach.** P1 (destination lock only, chosen by the owner), P2 (prefix locks too, recorded; a later cut), P4 (refuse `--break-lock` with several sources; rejected, it leaves a torn destination lock unrecoverable).
