The one design fork, what DEST's top level means, went through an AGY-FIRST consult and one negotiation round (`.clavity/seams/verify-several-top-level-fork.md`; replies in `.clavity/scratch/verify-several-top-level/`): the peer recommended the copy-mirroring reading and refuted the union-replica reading on the asymmetry argument of section 5; the driver refuted the peer's claim that the copy-mirroring reading needs no engine change (section 3, constraint C4). ## 1. Intent

`flux copy a b DEST` (cut 10c) copies several sources into one folder, each at `DEST/<name>`. `flux verify` (cut 14) takes one source. A person who made such a copy has to run one verify per root and add up the results. This cut lets them write the same command with `verify`:

```bash
flux verify a b DEST
```

and get one run, one summary, one exit status. It changes nothing for the one-source command.

## 2. Goals, non-goals, anti-goals

Goals
- Two or more sources, DEST last, mapped exactly as copy maps them (master 4.1, 18.3): each source against `DEST/<name>`, the roots in prefix order, the records streamed in one global `FluxPathKey` order with destination-relative paths.
- Refuse what copy refuses, before anything is read: a symlink source, a missing or special source, an unusable or reserved name, two sources taking one name (as bytes, or as one directory on the destination), a DEST that is a file.
- A user's own `.flux` directory or `.flux-root.lock` file copied into a root is user data and compares as such; a crashed copy's partial temporaries inside a root stay hidden.
- One summary and one exit status over all roots; `--json` says which sources the run covered.
- For a two-positional run the stdout records, the summary (human and JSON, keys and values), the stderr lines and the exit codes are byte-for-byte unchanged. `--help` and clap's argument-error text change with the `paths` signature (exit 2 either way); no test pins clap's text today.

Non-goals (each is a tracked follow-up or an existing one)
- Reporting DEST's top-level entries that belong to no root (strangers): see section 5. A follow-up may add a stderr advisory; it is not an `extra` record.
- `--exclude`, `--recursive` (ROADMAP phase 3), metadata and hardlink comparison, `--resume` with `--verify` (cut 15): unchanged from the cut 14 design's non-goals.
- Verifying a several-source copy that was ABORTED beyond what the records show: a root the copy never started simply reports `missing`.
- A cap on the number of sources: copy's cap (`source_cap`, `run/roots.rs:33-35`) is `open_writers_cap` applied to the descriptor limit, because a copy keeps a handle per root; verify holds nothing across roots.

Anti-goals (a pass that would make the command wrong)
- Hiding a user's `DEST/<name>/.flux` as control state, or reporting it `missing` (constraint C4).
- Reporting a copy's own residue in DEST (`DEST/.flux`, `DEST/<name>.flux-lock`, a `.broken.<id>` rename) as a discrepancy.
- Printing any record before a refusal that exits 2 (the cut 14 invariant "exit 2 with nothing on stdout").
- Changing the one-source JSON summary's shape.

## 3. Constraints (verified against the code at 613da2c)

- C1. The CLI resolver for several sources exists: `resolve::several` (`crates/flux-cli/src/resolve.rs:76-121`) takes the sources and DEST, refuses fewer than two sources, more than `cap`, a symlink source (`Stop::SymlinkSource`), a missing source (`Stop::Failed`), a special file, a source with no file name, and a DEST that exists and is not a directory (`Stop::Usage`); it canonicalises each source, takes the name as the final component, and returns `Vec<SourceSpec>` plus the canonical DEST with its absent remainder.
- C2. Name validation and prefix ordering live in the engine, not the resolver: `plan_roots` (`crates/flux-core/src/run/roots.rs:87-134`, `pub(crate)`) checks each name with `check_component`, refuses Windows device names and trailing dot or space on Windows, refuses the control-plane names (`.flux`, `.flux-dir.lock`, `.flux-root.lock`, any name ending in `.flux-lock`, ASCII case-insensitively, `:63-68`), refuses a name with no room for its lock (`prefix_lock_fits`), refuses two sources with one `FluxPathKey` (`DESTINATION_NAMESPACE_COLLISION`), and returns the specs sorted by key. It returns `RunError::Refused` with a `LockCode` and a detail string (`:37-43`). Copy calls it as its first group, before DEST is touched (`run/multi.rs:462-468`).
- C3. The merge engine takes one source root and one destination root. `Side::new` (`crates/flux-core/src/verify.rs:146-160`) wraps one walk; `verify_tree_notifying` (`:366-425`) runs `check_roots` (`:470-500`), builds the source side with `control_state = false` and the destination side with `control_state = true` (`:385-396`), and merges by key. `verify_file` (`:659-692`) compares one file, with the record path `dst.file_name()`. `verify_tree` (`:354`) is a wrapper. The cut 14 CLI calls these per `Job` (`crates/flux-cli/src/main.rs:755-837`).
- C4. The destination filter is a single boolean and hides a TOP-LEVEL `.flux` directory and `.flux-root.lock` file of whatever root it is given: `is_control_state` (`verify.rs:201-222`) tests the first component of the path relative to the destination root; the partial-temporary rule (`<head>.flux-partial.<32 hex>`, any depth, file or symlink) is in the same function, and the whole function is gated by `self.control_state` (`:262-266`). So a per-root run on `DEST/a` with today's filter would hide a user's copied `DEST/a/.flux` while the unfiltered source walk emits `a/.flux`, and report it `missing` (the mechanism of the fixture `a_source_dot_flux_directory_is_missing_when_dest_has_only_control_state`, `verify.rs:1203`). Master 259.3 (`FLUX_FULL_UPDATED_SPEC_V16.md:12949-12975`) says a source `.flux` is ordinary data that copy copies. Under several sources the control directory is `DEST/.flux` and the locks are `DEST/<name>.flux-lock`, both outside every root (several-sources design 3.4; `crates/flux-core/src/lock/site.rs:15-31`).
- C5. Output: a record prints as `{outcome}: {path}[: CODE][: detail]` with the path escaped by `display_path` (`crates/flux-cli/src/verify_report.rs:80-104`); `route_record` (`:212-227`) hides `match` without `--verbose` and adds the mount notice and the unreadable-extra warning on stderr from the record's path; the JSON summary body has exactly `source, dest, hash, matched, missing, mismatched, extra, unreadable, not_entered, bytes_hashed, exit` (`:139-176`); `summary_line` (`:127-137`); `dest_absent_line` (`:229-234`). Exit: `for_verify` (`crates/flux-cli/src/exit_code.rs:69-71`): 1 if the summary failed, else 0; usage 2; verify never exits 3.
- C6. Copy's several-source report precedent: one aggregated report, an OPTIONAL `roots` key present only for several sources, one stderr line per finished root `root <name>: <n> copied, <n> failed` (several-sources design 3.8; `report::root_lines`, `crates/flux-cli/src/report.rs:261-273`).
- C7. Master 4.2 (`FLUX_FULL_UPDATED_SPEC_V16.md:650-690`): verify "uses the destination mapping of Section 4.1"; `extra` is "at the destination, not in the source" and never changes the exit status. 18.3 (`:1394-1437`): roots visit in key order of their prefixes, each depth first, which yields global key order without buffering; the order does not depend on the command line.
- C8. The existing one-source CLI tests (`crates/flux-cli/tests/verify.rs`, 17 tests) pin the output shapes this cut must keep; `exit_2_for_nested_or_identical_roots_with_nothing_on_stdout` pins the no-records-before-exit-2 invariant.

## 5. Approaches considered

- O1, copy-mirroring (CHOSEN): each root is compared independently, `a` against `DEST/a`; DEST's other children are never visited. Why: a several-source copy is N root replications into DEST and asserts nothing about DEST's other children (18.3, several-sources design 3.2); `flux copy a DEST/a` followed by `flux verify a DEST/a` never reports DEST's siblings, so `flux verify a b DEST` reporting them would make the same folder read differently depending on how the copy was invoked; and the run never has to recognise Flux's residue in DEST, which after an aborted copy includes locks of roots this command does not name. Cost: the filter mode of C4 (a small engine change), plus the per-root plumbing.
- O2, union replica: one merge of a chained source stream (the roots in prefix order, `<name>` prepended) against one walk of DEST; every other top-level entry of DEST is `extra` and drained. Affordable (the merge touches a side only through peek and take; the one seam is the source-root join in `pair`, `verify.rs:575`), and faithful to 4.2's `extra` within a replica, but it makes DEST a replica the copy never claimed, floods the output when DEST is a shared folder or a prior one-source target, and needs a rule for every lock artifact a past run may have left. Rejected by the peer and conceded by the driver.
- O3, hybrid: O1 plus one listing of DEST's top level reporting strangers as shallow `extra` records. Rejected: a listing after the roots breaks global key order unless buffered, and a directory `extra` with no children is a record shape no consumer expects (cut 14 design 6.2 drains them).
- O4, a flag choosing O1 or O2: rejected as two behaviours to test and explain for a question the copy already answers.

## 6. Design

### 6.1 Command line and resolution
- `flux verify SOURCE... DEST`: two positionals are the cut 14 command, unchanged; three or more are the several-source command. `VerifyArgs.source: PathBuf` and `dest: PathBuf` (`main.rs:61-65`) become `paths: Vec<PathBuf>` with the three clap attributes `CopyArgs.paths` carries verbatim (`main.rs:99-101`): `required = true`, `num_args = 2..`, `value_name = "SOURCE... DEST"` (without the value name clap would print `<PATHS>...`), DEST the last. One positional or none is clap's own error, exit 2, nothing on stdout (test 15). The `Verify` variant's doc comment (`main.rs:52-56`, the `--help` text) lists the exit-2 cases as "a usage error, roots that are the same or nested, a refused source name, two sources that take one name".
- Every option applies to all roots: `--links`, `--cross-filesystems`, `--hash`, `--json`, `--verbose`.
- Nested sources (`flux verify a a/f DEST`) are allowed, as copy allows them (several-sources design, ruling R5): the prefixes `a` and `f` are distinct, so `a/f` is compared twice, under `DEST/a/f` and at `DEST/f`.
- Resolution reuses `resolve::several` (C1) with no cap (`usize::MAX`; section 2 non-goals). Its errors map as verify maps them today (`main.rs:770-790`): `Stop::Usage` is exit 2 with `error: <msg>` and no records; `Stop::SymlinkSource` and `Stop::Failed` are exit 1 with the existing stderr line and, under `--json`, the all-zero summary (R7 of cut 14), which for several sources carries `sources` (6.5). The symlink line names the first symlink source (`resolve::first_symlink`), as copy does. Resolution stops at the FIRST failing source, in command-line order (C1).
- A DEST that exists and is not a directory is `Stop::Usage` from `several` (its message says "copied"; the builder gives verify its own wording, "several sources cannot be verified against the existing file <DEST>", by passing the verb into `several`; a verify-side pre-check is NOT allowed, because `several` checks the sources first and DEST last (`resolve.rs:81-114`), so a missing source together with a file DEST is exit 1 with the stopped summary, as in copy, and a pre-check would turn it into exit 2).

### 6.2 Names, order and the root checks (before any read of the trees)
- The engine gets `pub fn verify_several(fs, specs: Vec<SourceSpec>, dest: &Path, opts, on_absent: &mut dyn FnMut(&OsStr), on_root_done: &mut dyn FnMut(&OsStr, &Summary), sink) -> Result<Summary, VerifyError>` in `crates/flux-core/src/verify.rs`. Its first step is `plan_roots` (C2): a refusal becomes `VerifyError::RefusedNames { reason: <the planner's detail> }` (section 8), which the CLI prints as `error: <reason>` with exit 2, the arm beside the one-source `RefusedRoots` arm (`main.rs:820-823`), nothing on stdout. The `LockCode` is not printed: for verify these are usage errors, and verify has no exit 3 (author's call A1). Nothing has been read yet, so no record precedes the exit.
- Second step, still before any listing: the root check of every FOLDER root, `check_roots(fs, src, DEST/<name>)` (C3), in prefix order. A `Refused` on any root ends the run with exit 2 and no records (the cut 14 invariant, C8). The engine returns the parts (`VerifyError::RefusedRoot { name, reason }`, section 8) and the CLI prints `error: root <name>: <dst>/<name>: <reason>; nothing was verified`, where `<name>` is escaped by `display_path`, `<dst>` is the canonical DEST that `resolve::several` returned (the one the engine was given; the one-source absent line also prints the canonical `dst`, `main.rs:802`), and `<reason>` is the existing clause WITHOUT its `; nothing was compared` tail (the constants at `verify.rs:440-442` carry that tail, and the by-path-alone note is appended after it at `:490-496`; the engine strips the tail and keeps the note, so the line reads `... the destination is the source or lies inside it (decided by path alone: ...); nothing was verified`). The clause says "the destination", which here is `DEST/<name>`, so the path is named; the CLI appends `; nothing was verified` last because no root ran.
- Aliasing names (open question of the round-2 panel): two roots whose names are distinct as bytes but one directory on the destination (`Data` and `data` on a case-insensitive filesystem). `plan_roots` compares keys as bytes (C2); copy detects the alias through its prefix locks and refuses it (`DESTINATION_NAMESPACE_COLLISION`, master 18.3, `run/multi.rs:854`), so no successful copy ever produced such a DEST, and verifying it would emit records that describe nothing real (each root reporting the other's files). Verify refuses it too, before any listing. Data flow: the root check of a FOLDER root returns, besides its verdict, the destination's identity when the check obtained one (`check_roots` reads it at `verify.rs:486`; today it discards it, so the check gains a return value or a thin wrapper); the engine fills a `HashMap<ObjectId, OsString>` (the first root's name per id; `ObjectId` derives `Hash`, `flux-fs/src/fs.rs:73-74`; `FileIdentity` does not, `:93`) from `Strong` identities ONLY, after the whole check loop. A root with no obtained identity (absent, unreadable, a failed identity query, `Weak`, `Unavailable`) takes no part and never refuses (copy's rule, `run/multi.rs:168-173`). On a repeated id the run ends with `VerifyError::RefusedAlias { a: OsString, b: OsString }` (the stored name and the current one, in prefix order), which the CLI prints as `error: roots <a> and <b> are one directory on this filesystem; nothing was verified` with both names through `display_path`, exit 2, no records. Precedence: the check loop runs first in prefix order, so a `RefusedRoot` wins over an alias refusal; any exit 2 discards every remembered verdict (an unreadable root recorded earlier prints nothing, as nothing precedes an exit 2). An absent `DEST/<name>` cannot alias and reports `missing` as usual; two FILE roots that alias, or a file root against a folder root of the same folded name, are not detected (`verify_file` reports what it finds; accepted boundary, section 11). An `Unreadable` result is remembered for that root and reported at its turn (6.3). The absent case is remembered too. A FILE root has no root check (cut 14 design 6.1), as today. The check phase KEEPS only what the walk phase needs, per root: the verdict (absent, unreadable with its error, or checked) and, for the alias rule, the destination identity; it keeps no directory handle open, so N roots cost N sequential opens and no descriptors are held across roots (A5 stands), and the walk phase reopens each root as `Side::new` does today. The window between a root's check and its walk can be long (root N is checked before root 1 is hashed); a root whose reopen fails in the walk phase (`Side::new` returning an error, as `verify_tree_notifying` handles at `verify.rs:385-396`) is one `unreadable` record `<name>` at its turn, the same as a check-phase unreadable; a verdict that went stale the other way (absent at the check, present at the walk) is not re-probed and reports `missing`, an accepted boundary (section 11) with the same shape as the one-source run, whose check and walk are also two separate opens.
- Why all checks first: a refusal of root `b` after root `a` printed records would exit 2 with records on stdout, which the one-source command never does.
- A `DEST/<name>` of the WRONG TYPE is a discrepancy, not a usage error. The probe is `fs.metadata(DEST/<name>)`, which does NOT follow links (`crates/flux-platform/src/std_fs.rs:311-315` is `symlink_metadata`; the `FileSystem` trait has no following stat, `crates/flux-fs/src/fs.rs:172`), exactly as the merge classifies an entry inside a tree and as copy classifies a root's target (`run/multi.rs:147-200`, which refuses "a Symlink is already there" for a folder root). So for a FOLDER root anything but a directory there, a symlink included (dangling or not), produces exactly one record, `<name>` `mismatched`, `kind` `dir`, detail `source dir, destination <file|symlink|other>` (the form `compare_pair` gives an entry), no walk, and the run goes on with the next root (exit 1 at the end). The probe runs before the root check, so `check_roots` (which opens with `destination_root`, a following open, `std_fs.rs:722-727`) never sees a non-directory. `NotFound` is the absent case (6.3). Any OTHER probe error (permission denied on DEST, a loop, a name too long) makes that root one `unreadable` record `<name>`, `kind` `dir`, the text led by `destination: `, the same as the `check_roots` unreadable path, and the run goes on. A FILE root's `DEST/<name>` goes through `verify_file`, whose own lstat-based classification already yields `source file, destination dir|symlink|other` or `missing` (C3); nothing changes there. Note the asymmetry with the one-source command, where a DEST the user NAMED is followed (`resolve::job`, `resolve.rs:48`): here `DEST/<name>` is a mapped entry, not a named root. Copy refuses both cases before transfer; verify reports them, because reporting the replica's type is its job (author's call A9).

### 6.3 The per-root run
- Roots run one after another in prefix order (C7). For each FOLDER root: if the check said absent, `on_absent(name)` fires (the CLI prints `dest_absent_line(DEST/<name>)`) and the source walk drains against an empty side; if it said unreadable, the one record is `<name>` `unreadable` with the side-prefixed text, as the `.` record today; otherwise the merge runs as `verify_tree_notifying` does, except that the destination side is built with the NESTED-ROOT filter mode (6.4). For each FILE root: `verify_file(fs, src, DEST/<name>, ..)`, whose record path is already `<name>` (C3).
- Builder shape (section 8): `verify_tree_notifying` is split into "check" and "walk a checked pair", and the walk takes the filter mode; the one-source entry points keep their signatures and pass the root mode.
- After each root, `on_root_done(name, &root_summary)` fires (the CLI prints the stderr line of 6.5), and the root's counts are added to the run's total.

### 6.4 Control-state filter modes
`Side` takes an enum instead of the boolean (C4):
- `None`: a source side; nothing hidden (today's `false`).
- `Root`: a one-source destination (today's `true`): a top-level `.flux` directory with all it holds, a top-level `.flux-root.lock` file, and `<head>.flux-partial.<32 hex>` files or symlinks at any depth.
- `NestedRoot`: a `DEST/<name>` destination: ONLY the partial temporaries at any depth. A `.flux` directory or a `.flux-root.lock` file at the root's top level is the user's, copied there from the source (259.3), and compares like any entry; a user file named `<head>.flux-partial.<32 hex>` is hidden exactly as it is under `Root` (the cut 14 boundary; a copy's temporary and a user file of that name cannot be told apart).
Why not simply "off" for the nested root: the partial rule is gated by the same flag (C4), and a crashed copy leaves its temporaries beside the targets inside the roots, where `Root` hides them today.

### 6.5 Records, order and output
- Every record a FOLDER root's merge produces is re-rooted before the sink sees it: path `<name>` for the root record `.`, else `<name>/<path>` (`Path::new(name).join(path)`). A FILE root's record is NOT re-rooted: `verify_file` already names it `<name>` (`verify.rs:667`, `dst.file_name()`), and prefixing again would print `f/f`. The wrong-type and unreadable records of 6.2 are emitted directly with path `<name>`. The mount notice, the unreadable-extra warning and the absent-DEST line therefore print the re-rooted path or `DEST/<name>` as they do today, with no change to `route_record`.
- Order: prefix order of the roots, each root in its own key order, is global key order (C7). No sorting, no buffering.
- Human mode (stdout): records as today (`match` only with `--verbose`); after each root one stderr line `root <name>: <matched> matched, <missing> missing, <mismatched> mismatched, <extra> extra, <unreadable> unreadable` (the five counts; `not_entered` and `bytes_hashed` only in the total), the operator's progress signal on a long run (the peer's point); then the summary line over the totals, unchanged in form. Every root NAME printed on stderr (the `root <name>:` line, the refusal prefix, the `DEST/<name>` of the absent-DEST line) goes through `display_path`'s escaping (C5), so a name with a newline or invalid bytes neither splits a line nor prints like another; copy's `to_string_lossy` root lines (`report.rs:268`) are not the model here. The DEST part of `DEST/<name>` is the canonical `dst` printed with `.display()`, as the one-source absent line prints its canonical `dst` (`main.rs:802`); the CLI builds the line from `dst` and the name through a new helper `root_absent_line(dst, name)` (section 8), because `dest_absent_line` takes one path and would not escape the name.
- `--json`: records as today, with re-rooted paths. The final `summary` object: for one source exactly today's keys; for several sources `source` is OMITTED and `sources` is present, an array of the sources, and the VALUES follow today's one-source rule element-wise: after a run that reached the roots, `sources` holds each root's canonical source (`SourceSpec.src`, C1) and `dest` the canonical `dst`, as the completed one-source summary prints the canonical `src` and `dst` (`main.rs:827`); a run that stopped during resolution (6.1) prints the paths as typed, as the one-source stopped path does (`main.rs:758-767`); `sources` is in COMMAND-LINE order on both paths (the resolver keeps that order; a record's first component is the name, so a script maps records to sources by name, not by position), every other key as today, in the key order `sources, dest, hash, matched, missing, mismatched, extra, unreadable, not_entered, bytes_hashed, exit`, `sources` taking `source`'s place. The one-source shape never carries `sources`. Why omit rather than keep the first source: a script reading `source` would believe only that one was verified (the peer's point); the precedent is copy's optional `roots` key (C6). The per-root stderr line prints under `--json` too: stderr is operational in both modes, as copy's root lines are (C6).
- A run that stops before any walk with exit 1 (6.1) prints, under `--json`, the all-zero summary with `sources` and `"exit": 1`, as the one-source command prints its summary (R7).

### 6.6 Exit codes
0 when nothing is missing, mismatched or unreadable over all roots; 1 when something is, or the run stopped before a walk as in 6.1; 2 for a usage error, a refused name, a refused root check, a refused alias (each with nothing on stdout). Never 3. `exit_code::for_verify` over the total summary is unchanged.

### 6.7 What `--help` and the README say
The synopsis `flux verify SOURCE... DEST`; "with several sources each is compared with DEST/<name>, as copy places it; what else DEST holds is not examined"; the exit codes as today; the GUARANTEES text (`verify_report.rs:7-19`) gains one bullet: "With several sources, only `DEST/<name>` for each source is compared; other entries of DEST are neither reported nor counted."

## 7. Calls made by the author (for the owner to check)

- A1. A refused name or a refused root check is a usage error (exit 2, `error: <detail>`), not copy's exit 3 refusal with `CODE: detail`: verify never changes anything, and the cut 14 design fixed its exit codes at 0, 1, 2.
- A2. The root checks of all roots run before any walk, so exit 2 never follows records (6.2).
- A3. Per-root stderr lines are kept (the peer's progress argument), with the five outcome counts only.
- A4. `source` omitted and `sources` added for the several case, in command-line order, canonical after a run that reached the roots and as typed when the run stopped during resolution (today's one-source rule, element-wise); `dest` follows the same rule; the engine takes the canonical DEST.
- A5. No source cap for verify (section 2).
- A6. DEST's strangers are a follow-up (TODO.md), not reported.
- A7. A user file named like a partial temporary inside a nested root stays hidden (the cut 14 boundary applies at any depth).
- A8. The per-root absent notice names `DEST/<name>`; with an absent DEST there is one line per folder root. Verify prints no single "DEST does not exist" line: a per-root line is what today's code produces and what a script already parses.
- A9. A `DEST/<name>` of the wrong type is one `mismatched` record for that root, not a refusal (6.2); copy refuses it because copy would have to overwrite it.
- A10. The per-root stderr line prints in both output modes (6.5).
- A11. A root whose `DEST/<name>` was earlier the target of a ONE-source copy holds that copy's `DEST/<name>/.flux`; under the nested-root mode it is reported `extra` (exit unaffected). Accepted boundary (section 11): verify cannot tell that directory from a user's, and a several-source copy never puts control state there.

## 8. Interfaces (names and shapes; bodies are the builder's)

- `flux_core::verify::ControlFilter { None, Root, NestedRoot }` (pub, since the CLI never names it the builder may keep it crate-private; the test fixtures in `verify.rs`'s `mod tests` name it).
- `flux_core::verify::verify_several` as in 6.2, taking the CANONICAL DEST, returning the TOTAL `Summary`; per-root summaries reach the CLI through `on_root_done`, which fires for EVERY root in prefix order, including a root that produced its one record without a merge (wrong type: `mismatched` 1; probe or root-check unreadable: `unreadable` 1; a file root: its one outcome), so the per-root lines and the total always agree.
- `flux_core::verify::VerifyError` gains `RefusedRoot { name: OsString, reason: String }` (a root check refused for root `name`; `reason` is the existing clause), `RefusedNames { reason: String }` (a `plan_roots` refusal, the planner's own text) and `RefusedAlias { a: OsString, b: OsString }` (6.2); the one-source `RefusedRoots { reason }` (`verify.rs:114-117`) is unchanged and reserved for the one-source root check; the CLI gets one arm per new variant, each exit 2 with nothing on stdout. The CLI formats and escapes names; the engine never formats a message for the terminal. The planner's detail embeds the source path with `.display()` (`roots.rs:92-131`), as copy prints it; that is an accepted boundary (section 11).
